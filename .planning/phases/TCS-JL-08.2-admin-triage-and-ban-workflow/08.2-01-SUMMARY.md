# Phase 8.2 Plan 08.2-01: Admin Triage & Ban Workflow Summary

**Phase 8.2 gave moderation its enforcement half: staff triage over both REST and Django Admin
with 08 §4.2's five actions, the §6 ban protocol (transaction commits the flag + audit line, an
idempotent Celery task then blacklists refresh tokens and deactivates devices), temporary 7-day
suspensions that lapse back on an hourly beat, and the whole announcement system 6.2 D15 deferred
here — model, publish→broadcast, expiry, and REST CRUD.**

## Performance

- **Ban protocol (MOD-06, D1/D2/D3):** `User.banned_until` (migration `accounts/0005`) +
  `moderation.services.ban_user` — one transaction sets `is_active=False`, the boundary, and the
  §11.1 log line, then `transaction.on_commit` dispatches
  `moderation.tasks.sever_banned_user_sessions` (reusing 2.2's `revoke_user_refresh_tokens` verbatim
  as promised). The task is idempotent and reports a `BlacklistedToken` **delta** (the primitive
  counts tokens *processed*, not newly blacklisted) and zero-rows the second time. Unban is
  one-way: `is_active` returns, devices/tokens stay severed. `moderation.tasks.auto_reinstate_users`
  + the new hourly beat entry `reinstate-suspended-users-hourly` close §6.1's temporary level.
- **Triage (MOD-05, D4/D5/D6):** `GET /api/v1/moderation/reports/` (§68 shape, staff-gated,
  severity-ordered by §4.1's static weights then newest-first, `?status=` whitelist-validated),
  `POST .../review/` with DISMISS/REMOVE_CONTENT/LOCK_POST/WARN_USER/BAN_USER
  (`DISMISSED` vs `RESOLVED`, `reviewed_by`/`reviewed_at`/`moderator_notes` written on every path),
  and `POST .../users/{id}/ban|unban/` (202/200). `ReportAdmin` ships §9.1's columns/filters/search
  plus five bulk actions, and `UserAdmin` gains ban/unban actions — **all delegating to the same
  services**, so Admin and REST cannot drift and a bare Admin `is_active` edit can no longer suspend
  an account without severing.
- **Login contract (R1):** 403 `ACCOUNT_SUSPENDED` is raised only after `check_password` proves
  ownership, so anti-enumeration holds (wrong password on a banned account still returns the generic
  401). 06 §2.6's conflicting test was updated deliberately, with the supersession in its docstring.
- **Announcements (D7, T8.6/T8.10):** `community.Announcement` (§7.1 shape) with `publish()` as the
  single idempotent trigger (False→True only — never a post_save signal); `broadcast_announcement`
  at the byte-exact reserved route name creates in-app `ANNOUNCEMENT` rows for every active verified
  user unconditionally (the push is preference-gated downstream, per 6.2 D13/D14) in
  `ANNOUNCEMENT_PUSH_CHUNK` batches, sending only the fixed zero-PII template; the reserved hourly
  `community.tasks.clean_expired_announcements` unpublishes lapsed rows; staff CRUD + an anonymous
  public read implement 04 §71–§75; `AnnouncementAdmin` publishes through `publish()`.
- **Audit (D9):** `log_moderation_action` emits one §11.1 JSON event per action with its keys as
  `extra=` LogRecord fields; no AuditLog model.
- **Gates:** **788 tests pass** (694 baseline + 94 new), `ruff check` + `ruff format --check` clean,
  `makemigrations --check` reports no drift, `manage.py check` clean, both migrations applied.

## Decisions Made

- **`transaction.on_commit` for the sever dispatch** rather than a direct `.delay()`: a ban performed
  inside an outer atomic block (which `resolve_report` is) must not enqueue a sever for a ban that
  later rolls back.
- **Validation surfaces stay consistent with the project's precedent:** body-shape errors use DRF's
  default rendering (`is_valid(raise_exception=True)`, exactly as 8.1's report endpoint does) while
  domain errors use the `{"error": {code, message}}` envelope.
- **Staff clients are their own `APIClient` instances in tests** — sharing the `api` fixture let a
  test that authenticated as a candidate also re-authenticate the staff client (found by a genuine
  test failure, not by inspection).

## Deviations from Plan

- **Migration number:** the plan said `0002_user_banned_until`; the accounts app already carried
  `0001`–`0004`, so it shipped as **`0005_user_banned_until`** (community's `0002_announcement` matched the plan).
- **Wiring test lives in its own file** (`apps/moderation/tests/test_celery_wiring.py`) instead of
  inside one of the four files the plan listed — it spans moderation/community/notifications/
  analytics, so no single listed file was the right home.
- **`broadcast_announcement_dispatch` seam added to `apps/community/tasks.py`**: `publish()` calls
  the seam, which forwards to `notifications.tasks.broadcast_announcement`. The reserved beat name
  lives in community and the reserved route name in notifications, so the seam is what keeps both
  byte-exact without importing the push app into `community.models`.
- **`UserAdmin.unban_selected_users` skips already-active rows** (idempotence) rather than writing
  an audit line per no-op.
