<decisions>
## Implementation Decisions

### Ban protocol sequencing
- **D1: Spec-literal transaction + Celery split (08 §6 verbatim).** Step 1 — one transaction commits `is_active=False` plus the moderation audit entry. Step 3 — a Celery task (`apps/moderation/tasks.py`, default queue) blacklists all outstanding refresh tokens (`accounts.services.revoke_user_refresh_tokens`, extracted in 2.2 verbatim for this) and deactivates all `Device` rows. Accepted consequence: a crash after commit before/during the task leaves a banned user with live sessions and active push devices until retry (manual re-ban is idempotent and re-fires the task). 04 §70's "Record the action" is the audit entry in the same transaction. The views return 202 Accepted (enforcement completes asynchronously).
- **D2 (consequence):** the task is idempotent and re-runnable; banning an already-banned user re-fires the severing task. The `unban` path reactivates the user, optionally clears `banned_until`, and does NOT reactivate devices (tokens stay revoked; users must re-register devices — sessions/severing stay one-way).
- **D3: Temporary suspensions ship (08 §6.1's 7-day level).** `User.banned_until` (nullable, admin-editable per §6.1's "Admin manual review only" restoration path) + a `community.tasks.auto_reinstate_users` Celery Beat task. If a ban is initiated with `duration_days=7` → temporary; `0`/None → permanent. Admin action on User rows supports both.

### Triage surface & actions
- **D4: Five actions (T8.7/MOD-05 authoritative over 04 §69's four).** `DISMISS` → status `DISMISSED`; `REMOVE_CONTENT`, `LOCK_POST`, `WARN_USER`, `BAN_USER` → status `RESOLVED`. `reviewed_by`/`reviewed_at`/`moderator_notes` written on every action; `moderator_notes` stays internal (04 §63, §14.5).
- **D5: BAN_USER review-decision and standalone ban endpoints share one service** (`moderation.services.ban_user`), differing only in the optional report linkage. DELETE `/api/v1/moderation/reports/{id}/` does not exist — the REST surface has no report deletion; §10's day-90 minimization is out of scope (Deferred).
- **D6: Queue ordering = static severity weights (08 §4.1).** `REPORT_SEVERITY_WEIGHTS` (SCAM 100 → OTHER 10) as code constants, then `-created_at`. §4.1's log2(report_count+1) velocity multiplier is a recorded divergence — the target-type-agnostic reviewer works the whole queue at MVP scale. `LOCK_POST` is valid only on post-targeted reports (400 otherwise); `REMOVE_CONTENT` on a tombstoned target re-flags and resolves (idempotent).

### Announcements
- **D7: Full T8.6+T8.10 scope.** `community.Announcement` per 08 §7.1 (draft → `is_published=True` → pinned + Celery FCM broadcast to active devices of users with `notify_on_announcements=True` and `push_enabled=True`, zero-PII payloads) + `clean_expired_announcements` with the **exact reserved route name** `community.tasks.clean_expired_announcements` (the 7.2 route-mismatch lesson) + in-app `ANNOUNCEMENT` notification to every candidate (the v1 producer for 6.1's deferred type). Preference gating gates the *push* only — the in-app row is not preference-gated, mirroring 6.2 D13/D14's semantics for MODERATION/SYSTEM.
- **D8:** announce-side REST surface = full 04 §71–§75 (staff write CRUD + `GET /api/v1/announcements/` public-read of published, non-expired rows ordered pinned→published; unauthenticated GET accepted as the landing/feed read contract).

### Audit trail
- **D9: Structured logging only — no AuditLog model.** Every moderation action emits §11.1's `MODERATION_ACTION_TAKEN` JSON event (moderator_id, report_id/target_id, action, reason, notes) through the `moderation` logger. The durable per-report record is `Report.reviewed_by/reviewed_at/moderator_notes`. §6's AuditLog model, §4.2.4's infraction counting, and §10's day-90 minimization are recorded divergences (relevant because D1 commits the audit entry in the ban transaction — that entry is the §11.1 log line).
</decisions>

<specifics>
## Specific Ideas

- The review endpoint is the single write gate: both the REST review and the Admin bulk actions call the same `moderation.services` functions, so an Admin action can never drift from the API semantics (08 §9.1's actions delegate).
- BAN_USER from a report resolves the report and bans the report's *content author* (post.author/comment.author) — the standalone ban endpoint takes the user id directly. Disambiguation is deliberate (§4.2.5's BAN_USER is always about the content author).
- Temporary vs permanent is a request field (`duration_days`, 0 = permanent) validated against §6.1's table; `banned_until=None` + `is_active=False` = permanent.
- Structured log events include report id when present so §11.1's report_id field stays populated for review-path actions.

</specifics>
