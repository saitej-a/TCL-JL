# Phase 6.1: Notification & Device Models - Context

**Gathered:** 2026-09-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Roadmap plan 06-01 (T6.1): the **model layer only** of the notifications system —
`Notification`, `Device`, and `NotificationPreference` in a new `apps/notifications`
app, with the migration carrying the compound indexes for read tracking (NOTIF-01).
No serializers, views, URLs, or permissions (6.2 / plan 06-02); no Celery tasks,
Firebase SDK, push payloads, or pruning (6.2/6.3 / plans 06-02, 06-03). The
dashboard keeps its explicit `0` unread placeholder (4.2 D1) — 6.1 ships the
*seam* (unread-count helper) but does not wire the dashboard call.

<decisions>
## Implementation Decisions

### Type vocabulary
- **D1 — Ship all 7 spec types.** `COMMENT`, `REPLY`, `VOTE_MILESTONE`,
  `ANNOUNCEMENT`, `MODERATION`, `TIMELINE_REMINDER`, `SYSTEM` — the full
  07 §3.1 `NotificationType` set. Phase 8's moderation alerts and the
  TIMELINE_REMINDER beat reuse them with **zero migrations**; v1 code paths
  produce only 4 of the 7, and the plan must say so plainly rather than imply
  every type has a live producer at launch.
- **D2 — Django `TextChoices` on the model** (07 §3.1's exact pattern):
  `type = CharField(max_length=32, choices=NotificationType.choices,
  default=SYSTEM)`. The taxonomy is closed and system-owned — the
  settings-driven validator pattern (5.1 D1 / 3.1 D3) is deliberately **not**
  applied here, because notification types drive code dispatch in 6.2/6.3; a
  settings-added unknown type would reach code with no handler, so the
  flexibility buys nothing.

### Message & PII
- **D3 — Snapshot title/message at creation.** The stored row is an immutable
  historical record per 07 §3.1 (stored `title`/`message` columns) and 07 §4.1.1
  (literal templates). Deleting the post later cannot rewrite what a user was
  told. Read-time composition was rejected: it would make 6.2's list endpoint
  and every push task re-derive text and open re-render drift.
- **D4 — Anonymity-safe labels are baked in at composition.** The (6.2)
  notification-creation service composes text through `AuthorPublicSerializer`
  semantics: an ANONYMOUS actor (the default) renders as a neutral label
  ("A candidate"), a DISPLAY_NAME actor renders as their handle. What lands in
  the row is already anonymity-safe, so 6.2's zero-PII push payloads and the
  in-app rows are guaranteed **once, at creation** — not re-derived per reader
  or per endpoint.

### Read-state rules
- **D5 — DB-level read-state integrity, mirrored in application code.** Add
  `CheckConstraint(check=Q(is_read=False) | Q(read_at__isnull=False),
  name="notification_read_state")`. Same hard-guarantee tier as 5.1's
  `unique_user_post_vote`: a row can never claim unread while carrying a read
  timestamp, no matter which writer (API, admin, management command) touches it.
  Application layer (service + `clean()`) must translate violations into clean
  application errors rather than surfacing `IntegrityError`. This is an
  **addition beyond 07 §3.1's schema** — the verification record must report it
  as a known, deliberate deviation.
- **D6 — Unread-count helper ships in 6.1.** A model/manager helper
  (`Notification.objects.unread_count_for(user)`) over the compound index is
  the wiring seam 4.2 D1 promised. The dashboard keeps its `0` placeholder
  until 6.2 wires the call (6.1 stays model-only), but the helper's contract is
  test-pinned now so the planner designs 6.2 against a fixed interface.

### Claude's Discretion
None — all six decisions were selected and confirmed by the user.

</decisions>

## Existing Code Insights

### Reusable Assets
- `apps/community/models.py` — the repo's model-layer template: UUIDv4 PKs,
  named compound indexes (`idx_*`), `Meta.ordering` justified in comments,
  docstrings that name the spec sections and locked decisions.
- `AuthorPublicSerializer` (`apps/candidates/serializers.py`, 3.2) — the
  anonymity-resolution seam D4 builds on; already renders the anonymized 2.2
  row as anonymous with no email, with redaction tests.
- `apps/community/services.py` + `tombstones.py` — the service-layer + helpers
  pattern 6.2's `create_notification` should follow (5.2 P12 already
  documented the hook call site).
- Test infrastructure from Phases 1–5.2: 441-test green suite, ruff gates,
  migration-drift checks.

### Established Patterns
- **UUIDv4 PKs on every model** (03 §18) — all three new models follow.
- **Named compound indexes with descending support** (4.1 / 5.1 P3) — the
  notification indexes land in the same style; 07 §3.1 specifies
  `(recipient, is_read, -created_at)` and `(recipient, -created_at)`.
- **Hard-DB vs application-level guarantees are documented as unequal** (5.1
  P4) — D5 adds a third hard guarantee (CheckConstraint) to sit beside 5.1's
  unique vote constraint.
- **`choices` vs settings-driven vocabularies are chosen per domain** — D2
  documents why notifications diverge from 5.1 D1's category choice.
- **CASCADE from User is the spec default and is safe here** — 2.2's
  anonymize-delete never hard-deletes users (same reasoning 5.1 D2 recorded
  for the PROTECT fork; notifications/devices follow 03's explicit CASCADE).

### Integration Points
- `apps/timeline/services.py:212` — `community.unread_notifications: 0`
  placeholder, wired to D6's helper in 6.2.
- `apps/community/services.py` — comment/reply creation call site documented
  by 5.2 P12 as the Phase 6 notification hook.
- `config/settings/` — new `apps.notifications` app registration (3.1/4.1/5.1
  app-registration pattern).
- `devices`/`notification` related_names in 07 §3 (`devices`,
  `notifications`, `notification_preferences`) — free on the User model; the
  accounts app has no conflicting relations.
