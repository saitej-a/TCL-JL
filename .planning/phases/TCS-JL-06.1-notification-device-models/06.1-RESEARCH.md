## 2. Spec deltas & ambiguities the planner must resolve

1. **Index naming.** 07 §3.1–3.2 give `Meta.indexes` with **no names** (`(recipient, is_read, -created_at)`, `(recipient, -created_at)` on Notification; `(user, is_active)` on Device) plus field-level `db_index=True` on several columns. Repo convention (4.1 / 5.1 P3) is **named `idx_*` compound indexes**. Resolution input: name them repo-style (`idx_notif_recipient_read_created`, `idx_notif_recipient_created`, `idx_device_user_active`); keep field-level `db_index` flags exactly as the spec writes them (literal compliance; storage cost trivial at MVP scale) — or drop the redundant ones and document. Planner pins one.
2. **`Device.__str__` (07 §3.2)** renders `self.user.email`. Server-side only, but it puts PII into logs/admin lists; 03 §8 already declares tokens sensitive. Micro-deviation candidate: render without email. Planner pins.
3. **`mark_as_read()` (07 §3.1)** is a model method with `save(update_fields=["is_read", "read_at"])`. Model-layer → ships in 6.1. With D5 it is also the sanctioned single-field-pair write path; 6.2's bulk mark-all-read service must respect the constraint too (set both, or use the manager).
4. **Unread count (D6).** No manager precedent exists in the repo (all aggregation so far is `annotate()` at view layer). Options: custom `NotificationManager.unread_count_for(user)` vs module function in a services file. Manager is model-layer and keeps 6.1 free of service files that only 6.2 exercises. `filter(recipient=user, is_read=False).count()` walks the `(recipient, is_read)` prefix of the compound index.
5. **NotificationPreference lifecycle** (gray area **not** discussed): 07 §3.3 defaults all six flags `True`; no producer of preferences exists until 6.2. Recommendation: no `post_save` signal (import-time signal registration is a known test-ordering hazard; explicit is testable); a `get_or_create_for(user)` classmethod on the model ships in 6.1 so 6.2 has one owner and endpoints cannot invent a second accessor.
6. **CASCADE dormancy.** 03's relationship table: `User → Device` and `User → Notification` **CASCADE**. Safe for the same reason 5.1 documented: 2.2 anonymizes rather than deletes user rows, and 03's deletion flow removes devices explicitly. Keep spec CASCADE; document dormancy in docstrings (5.1 D2's pattern). The F1 decision (profile deletion vs user deletion) does not interact — F1 deletes the *profile*, never the user row.
7. **Type enum (D1/D2).** Ship all 7 `NotificationType` values as a nested `TextChoices` with 07 §3.1's exact labels; `default=SYSTEM`. `DeviceType` WEB/ANDROID/IOS/OTHER, default WEB, per 07 §3.2.
8. **Zero-PII / D4 boundary.** 6.1 provides the *columns*; composition semantics (anonymity-safe labels) are 6.2's service contract. Research confirms `AuthorPublicSerializer` (3.2) is the seam 6.2 will reuse — nothing to build in 6.1 beyond not baking any rendering into the model.

## 4. Risks / landmines

- **R-1:** Django renders `CheckConstraint` in `schema_editor` only at migration time — a test that flips `is_read=True` without `read_at` via `QuerySet.update()` must expect `IntegrityError` (not `ValidationError`); the application-level translation is `clean()`/service behavior, and the plan must test **both** layers distinctly.
- **R-2:** `--reuse-db` means the check constraint must exist in the migration, or the test DB silently lacks it (pytest truncates but does not re-migrate). Never create the constraint via `RunPython`.
- **R-3:** `TextField(unique=True)` on `fcm_token` creates a btree index on an unbounded text column — fine for MVP scale; PostgreSQL will cap at ~2704 bytes for the index entry. FCM tokens are ~150–250 chars, no practical risk; note it, don't engineer for it.
- **R-4:** `last_seen_at = auto_now` + `updated_at = auto_now` on `Device` are two fields that both mutate on every save — spec has both; keep both, but `update_fields` writers (6.2's token refresh) must remember `last_seen_at` is not auto-updated when `update_fields` excludes it... actually `auto_now` fields only fire when included in the update or on full save — document for 6.2.
- **R-5:** Index-only scans for the unread count require the count query to touch only indexed columns — `(recipient, is_read)` prefix qualifies; do not add `.order_by()` to the count.
