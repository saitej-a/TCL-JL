## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The plan's pinned index name was rejected by Django**
- **Found during:** Task 1 (`makemigrations`)
- **Issue:** `idx_notif_recipient_read_created` is 32 characters; Django caps index names at 30 and raised `notifications.Notification: (models.E034)` — a `SystemCheckError` that blocks the whole app, not a warning.
- **Fix:** Shipped `idx_notif_recip_read_created` (27 chars) — same repo-style naming convention, same columns, same `DESC` ordering. Tests, the drill and the plan's gate list all reference the shipped name.
- **Files modified:** `apps/notifications/models.py`
- **Verification:** `makemigrations --check` clean; psql shows `idx_notif_recip_read_created btree (recipient_id, is_read, created_at DESC)`.
- **Committed in:** `ef8bbbd`

**2. [Rule 1 - Bug] The plan described `clean()`'s mirror in the wrong direction**
- **Found during:** Task 2 (writing the application-layer test)
- **Issue:** The plan's R-summary prose said `clean()` raises "when `is_read` is falsy while `read_at` is set". That combination is *legal* under `Q(is_read=False) | Q(read_at__isnull=False)`; the constraint's only forbidden state is `is_read=True` with `read_at IS NULL`. Implementing the prose would have produced a mirror that rejects exactly the rows the database accepts — and the plan's own test matrix ("three legal states: `False/None`, `True/<ts>`, `False/<ts>`") already contradicted it.
- **Fix:** `clean()` mirrors the constraint as written; tests assert the correct rejection *and* that all three legal states pass `clean()`.
- **Files modified:** `apps/notifications/models.py`
- **Verification:** `test_clean_raises_validation_error_with_the_stable_code`, `test_clean_accepts_every_legal_state`.
- **Committed in:** `ef8bbbd` / `ba6d8da`

**3. [Rule 3 - Staging] Task 1 and Task 3's model code landed in one commit**
- **Found during:** Task 1 (planning the migration sequence)
- **Issue:** Executing Task 1 literally (`Notification` only) then Task 3 (`Device` + `NotificationPreference`) requires regenerating `0001_initial` as a three-table migration. Since `docker compose run web` inherits `RUN_DB_MIGRATIONS=1`, the Notification-only migration would have been applied to the dev database first, leaving that database claiming `0001_initial` was applied while `notifications_device` did not exist — Task 5's psql proof would then fail for a reason unrelated to the code.
- **Fix:** All three models were written before the single `makemigrations`, so exactly one schema artifact ever existed. Task boundaries were preserved for everything else: the per-task test files still landed in their own commits, and every task's `<verify>` command was run in order against the growing suite.
- **Files modified:** `apps/notifications/models.py` (content as planned)
- **Verification:** `showmigrations notifications` → `[X] 0001_initial`; `\d notifications_device` exists on the live database.
- **Committed in:** `ef8bbbd`

**4. [Rule 1 - Bug] Two of my own tests were wrong and the drill/run caught them**
- **Found during:** Task 3/4 first test run
- **Issue:** the device-ordering test built its fixture user by creating a third device (`make_device().user`), so the assertion saw three rows; the unread-count test created a "read" row with `read_at=None`, i.e. the illegal pair.
- **Fix:** both rewritten (explicit `make_user()`; read rows carry a timestamp).
- **Files modified:** `tests/test_devices_and_preferences.py`, `tests/test_unread_count.py`
- **Verification:** 45/45 green afterwards.
- **Committed in:** `329deae` / `74ee17b`

### Not a deviation, but worth recording: the planner's index-prefix claim is a *shape* claim, not a runtime guarantee

RESEARCH R-5 says the unread count "walks the `(recipient, is_read)` prefix of `idx_notif_recip_read_created`". Live `EXPLAIN` shows PostgreSQL choosing `idx_notif_recipient_created` (the narrower index) plus `Filter: (NOT is_read)` at MVP data volumes — a cost decision, and the right one for a handful of rows. The shipped index shape is correct for the unread-list read path 6.2 will build; what 6.1 guarantees is the shape and the absence of a sort, both asserted. The drill checks that a notification index is used and that no `Sort` appears, rather than naming the planner's choice.

The model half (models, read tracking, indexes, the count seam) is done; 6.2 closes the requirement.
