## 2. Integration points (verified in code)

### Scanner call sites — exactly four (CONTEXT D4/D5)
1. `PostListCreateView.post` — `apps/community/views.py` ~L268: calls `create_post(request.user, **serializer.validated_data)`; scan `title`+`body` before calling.
2. `PostDetailView.patch` — ~L292: sets `title/body/category` from `serializer.validated_data`, then `full_clean()`+`save()`; scan the **merged** result (existing stored values + incoming partial fields) before save.
3. `CommentListCreateView.post` — ~L372: calls `create_comment(post, request.user, body=..., parent=...)`; scan `body` first.
4. `CommentDetailView.patch` — ~L421: sets `comment.body`, `full_clean()`, `save()`; scan merged body.

`moderation/heuristics.py` imports only `re` — no model imports — so `community → moderation` import direction creates **no circular import** (moderation's model-level dependency on community is via lazy string FKs `"community.Post"`).

### Error envelope
`CommunityErrorMixin.handle_exception` (`apps/community/views.py` ~L188) translates service exceptions into `{"error": {"code", "message"}}` via typed `APIException` subclasses (`_Locked`, `_DuplicateVote` are the house pattern). Add `_ScamPatternDetected` (400, `scam_pattern_detected`) and `_DuplicatePost` (400, `duplicate_post`) in the same style. The reports endpoint lives in `apps/moderation` with its own views module — reuse the same envelope shape (project-wide one body style, per 3.2/4.2).

### Throttle wiring
- Rates live in `config/settings/base.py` `REST_FRAMEWORK["DEFAULT_THROTTLE_RATES"]` (currently `auth_*`, `community_writes: 30/min`, `device_registration`, `notifications_reads`, `analytics_reads`). Add `"reports": "10/hour"` per spec.
- **Landmine (7.2 R1, HIGH):** DRF `ScopedRateThrottle.allow_request` does `self.scope = getattr(view, 'throttle_scope', None)` and returns `True` (allow) when the *view* has no scope — a class-level scope alone is inert. Community's six write views have exactly this defect today. 8.1's `ReportListCreateView` must set **both** `throttle_classes` and `throttle_scope = "reports"` on the view, and a test must assert the bucket engages (429 after 11th request within the hour).
- `PostListCreateView` (post create) declares **no `throttle_classes` at all** — 5.2's known HIGH defect F2. The scanner integration must not be gated on fixing it (out of 8.1 scope), but the debounce limits the worst duplicate-flood case.

### Debounce mechanics (CONTEXT D6)
- Cache backend is `django_redis` under `KEY_PREFIX = "tcsjl"` (`config/settings/base.py` CACHES). Use Django's cache framework (`django.core.cache.cache.get/set`) — never a raw Redis client (6.2 D3) — so tests keep running on LocMemCache.
- Key shape: `moderation:dup:post:{md5hex}`; value: author id (for diagnostics); TTL 3600 read from a settings constant `DUPLICATE_POST_WINDOW = 3600` (read at call time, house style).
- Two hashes per create: `md5(f"{author_id}:{title.strip().lower()}")` (T8.5) and `md5(f"{author_id}:{normalized_body}")` where normalization = collapse whitespace + `.strip().lower()` (CONTEXT D6). Either hit → 400 `duplicate_post`.
- `hashlib.md5` used only as a non-crypto dedup key (matches spec); inputs bounded by model `max_length`s (title 200, body 10000 per community models) — no DoS surface.
- Only the **create** path debounces (spec: "cannot post identical titles… within 60 minutes"); edit path deliberately not debounced — editing your own post twice in an hour is legitimate.

### Report model hard-law (beyond the spec's given schema)
- The XOR CheckConstraint ships as given. Add **two conditional `UniqueConstraint`s** as the database law for dedup: `UniqueConstraint(fields=["reporter", "post"], condition=Q(status="PENDING"), name="unique_pending_report_per_post")` and the comment twin (04 §66's `UNIQUE(reporter, post, status=pending)` made race-safe). The application-level query check remains for the friendly 400 `DUPLICATE_REPORT` envelope; IntegrityError maps to the same envelope (house pattern: 5.1 P4 double-enforcement, 6.1 D5).
- `post`/`comment` FKs are `SET_NULL, null=True` per §3.2: when the target post is hard-deleted (never blocked for posts, 5.1 D4) the report row survives with `post=NULL` for 8.2's audit trail — but note the XOR constraint then sees `post=NULL, comment=NULL`, which a hard delete would violate on update. Mitigation: `SET_NULL` fires on the *Post* row deletion; Django's CheckConstraint is evaluated on the Report row, and Post deletion triggers a Report update → constraint breach. **This is a real schema conflict in §3.2's given code**: resolve by keeping the XOR constraint but making hard-deleted targets set both FKs consistently is impossible (only one is set). Resolution: `on_delete=SET_NULL` only breaches if the report is updated; Django emits an `UPDATE reports SET post=NULL` which re-validates constraints → IntegrityError at Post-delete time. Since 8.1 controls the schema, the researched fix: wrap target FK with `on_delete=models.SET_NULL` **and** relax the XOR constraint to also allow `(post IS NULL AND comment IS NULL)` — no; that re-opens "neither" at creation, which `clean()` still blocks. Spec-true alternative: keep XOR strict and use `on_delete=models.CASCADE` for `post`/`comment` so a hard target delete removes the report rows too. Trade-off: loses audit trail. **Decision for planner:** strict XOR + CASCADE (evidence preserved via moderator_notes/soft-delete path; 5.1 D4 says post hard-deletion is never blocked, and a report on a vanished target has no triage value), documented as a deliberate deviation from §3.2's SET_NULL with the constraint-conflict rationale. Alternatively keep SET_NULL and accept that a post hard-delete fails while reports exist (PROTECT-like behavior via constraint). Planner must pick one and record it; CASCADE recommended.

## 3. Risks & landmines

1. **Throttle inertness** (7.2 R1) — scope on the view or the rate limit silently does nothing. Test asserts 429.
2. **§3.2's SET_NULL vs XOR conflict** (above) — must be resolved deliberately in planning, not discovered at Post-delete time.
3. **False positives on legitimate content** — "no guaranteed joining letter" matches `(guaranteed|direct|immediate)\s*(joining|...)`. Accepted by user (D7/D8): category-naming 400 is the mitigation; patterns are deploy-gated. Tests must include the false-positive *behavior* contract (message names category, never the pattern).
4. **Edit-path merge semantics** — PATCH is partial; scan the post-save entity state, not just the payload, so `title` unchanged + `body` newly scammy still blocks.
5. **Debounce key TTL vs cache `KEY_PREFIX`** — `tcsjl:` prefix + our key is fine; don't use `cache.delete_pattern` (django_redis-only; breaks LocMemCache tests).
6. **`CommunityWriteRateThrottle` vs `reports` scope** — the reports view uses its own throttle class; do not attach `community_writes` (different budget).
7. **Report on tombstoned content** — 08 §3.3's flow doesn't forbid it; a deleted target can still be reported (evidence), and `Post._get_live_post(for_read=False)` semantics must not leak into the reports path (reports resolve targets directly, not via the community helpers that refuse tombstones).
