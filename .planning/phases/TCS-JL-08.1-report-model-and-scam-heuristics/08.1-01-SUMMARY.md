# Phase 8.1 Plan 08.1-01: Report Model & Reporting Endpoint Summary

**Phase 8.1's first plan put moderation on the map: a new `apps/moderation` app whose `Report`
model enforces the exactly-one-target XOR law in the database, pending-dedup enforced twice
(application query + two conditional UniqueConstraints), and an authenticated, throttled
`POST /api/v1/reports/` speaking 04 §63–§65's contract.**

## Performance

- **Model (MOD-01/MOD-02):** `Report` ships 08 §3.2's schema verbatim — UUID pk, the seven
  `ReportReason` and four `ReportStatus` TextChoices, reporter/post/comment/reason/description/
  status/reviewed_by/reviewed_at/moderator_notes, the four Meta indexes (renamed to ≤30-char
  identifiers: `idx_report_status_created`, `idx_report_post_status`, `idx_report_comment_status`),
  and the `report_exactly_one_target` CheckConstraint (shipped with `condition=` per the Django 6.0
  deprecation the 6.1 R1 precedent already flagged). `clean()` mirrors the XOR with §3.2's message.
- **Deviation (recorded in the model docstring):** `post`/`comment` FKs use `CASCADE`, not §3.2's
  `SET_NULL`. SET_NULL would UPDATE a surviving report to (NULL, NULL) on target hard-delete and
  breach the XOR constraint at delete time; CASCADE keeps every report pointing at a live target
  while post hard-deletion stays unblocked (5.1 D4). Proven by `test_hard_deleting_post_deletes_its_reports`.
- **Dedup (MOD-03):** `unique_pending_report_per_post` / `unique_pending_report_per_comment`
  conditional UniqueConstraints make 04 §66's rule race-safe; the service's §3.3 query check raises
  the typed `DuplicateReportError` for the friendly 400 `duplicate_report` envelope, and a racing
  IntegrityError maps to the same envelope (5.1 P4 double-enforcement parity).
- **Endpoint (MOD-03):** `POST /api/v1/reports/` (04 §63–§65): authenticated (IsAuthenticated +
  IsActive + IsVerified), exactly-one-target validation at the serializer, 201 returning exactly
  `{id, status: PENDING, message: "Report submitted successfully."}` — no target body, no reporter
  email (T-08.1-02). Tombstoned targets stay reportable (evidence; 08 §3.3 has no tombstone guard).
- **Throttle:** `ReportRateThrottle` (`reports` scope, 10/hour in `DEFAULT_THROTTLE_RATES`) with
  **`throttle_scope` declared on the view** — the 7.2 R1 landmine — and `test_report_throttled_after_ten_per_hour`
  asserting the 11th request within the hour draws 429.
- **Gates:** 663 tests pass (638 baseline + 25 new), `makemigrations --check` clean after
  `0001_initial` (which contains all three constraint names), `ruff check` + `ruff format --check`
  clean. First migration since 6.1 — the zero-migration streak ends by design.

## Decisions Made

- **CASCADE over SET_NULL** (above) — the plan's pre-declared deviation, proven necessary by the
  constraint's own semantics rather than discovered at runtime.
- **`_raw_create` test helper uses `bulk_create`** — `objects.create()` calls `save()`/`clean()`,
  which would mask DB-level enforcement; `bulk_create` skips both, so the two "DB refuses" tests
  prove the constraint lives in SQL.
- **Indexes named explicitly** — Django rejects index names over 30 chars; the plan's field lists
  left names to the executor (6.1 R1's lesson applied).
