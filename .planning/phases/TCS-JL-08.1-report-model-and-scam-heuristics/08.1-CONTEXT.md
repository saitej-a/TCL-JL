# Phase 8.1: Report Model & Scam Heuristics - Context

**Gathered:** 2026-09-22

<domain>
## Phase Boundary

`apps/moderation` — a new Django app delivering MOD-01..04: the `Report` model with the database-level `report_exactly_one_target` XOR check constraint, the authenticated `POST /api/v1/reports/` endpoint with pending-report deduplication and a 10/hour throttle, and `moderation/heuristics.py` — automated scam regex scanning that intercepts matching posts and comments with a 400 before publication. <decisions>
## Implementation Decisions

### Flagged-content action (scam scanner verdict)
- **D1: Hard-block, never publish.** A post or comment whose (title + body) matches any scam pattern is refused with `HTTP 400` and code `scam_pattern_detected` before any row is written. The second branch of 08 §8's pipeline (publish + auto-create a PENDING SPAM report) is deliberately not built — the roadmap's "scam posts are intercepted pre-publication" is the authority.
- **D2: The 400 names the violation category, not the regex.** The response detail describes the category (e.g. "possible fee solicitation or credential request") so honest users can fix false positives, but never echoes the matched pattern text — 08 §8.1's returned `matched_pattern` is an internal return value only, never surfaced in the HTTP response, because handing scammers the patterns hands them the evasion recipe.
- **D3 (consequence):** Because 8.1 blocks rather than reports, no automatic Report rows are created by the scanner. The PENDING → triage loop in 8.2 is fed by human reports only.

### Scan scope & timing
- **D4: Both surfaces — posts and comments.** MOD-04's wording is "post bodies", but 08 §8's pipeline diagram runs both submissions through the scanner; a fee demand in a comment is as dangerous as one in a post. One scanner, two call sites.
- **D5: Create AND edit.** Both `POST` and `PATCH` paths for posts and comments run the scanner. Without edit-path scanning, the block only guards the front door — a clean post could be edited into a scam afterwards. (5.2 P6 allows author edits of both content types, so both edit paths exist and must be covered.)

### Debounce breadth
- **D6: Title + body hashes, posts only.** T8.5's MD5 of `(author_id + title.strip().lower())` is joined by a second hash of `(author_id + normalized body)`, both stored in Redis with a 3600s TTL, both returning `DUPLICATE_POST` 400 on a hit. Rationale: catching identical text under a new title is the common bot pattern. Comments are NOT debounced — comment velocity is already bounded by the existing community write throttle, and comment flooding is cheap to handle in 8.2's queue.

### False-positive handling (pattern source)
- **D7: Code constants in `moderation/heuristics.py`, spec-literal.** The four SCAM_PATTERNS from 08 §8.1 ship as module-level compiled constants — no settings indirection. Pattern tuning therefore requires a deploy; the user accepted this trade-off in favor of spec fidelity.
- **D8 (consequence):** The category-naming block message (D2) is the primary false-positive mitigation. If it proves insufficient, the fix path is a code change.

</decisions>

## Existing Code Insights

### Reusable Assets
- `apps/community/permissions.py` — `CommunityAccess` (active + verified gate) for the reports endpoint's permission stack; `IsModerator` (staff-only) exists already for 8.2.
- `apps/community/throttles.py` — `CommunityWriteRateThrottle` pattern to mirror (scoped, settings-read rate); 8.1 adds `ReportRateThrottle` in `apps/moderation/throttles.py` with the scope declared **on the view** (7.2 R1).
- `apps/community/tombstones.py` — soft-deletion masking; reports may target already-deleted content, and `target` data must survive `SET_NULL` semantics.
- `apps/community/validators.py` — existing input validation conventions.

### Established Patterns
- **Thin views + service layer** (5.2/6.2/7.2 pattern): validation and invariants in `services.py`, thin APIViews translating domain errors to HTTP codes.
- **Error envelope**: `{"error": {"code": ..., "message": ...}}` with `400` codes like `DUPLICATE_REPORT`, `DUPLICATE_POST`, `scam_pattern_detected` (04 §66's `DUPLICATE_REPORT` precedent set by 5.2's error codes).
- **Model guardrails**: `CheckConstraint` + mirrored `clean()` (6.1 D5's `read_state_inconsistent` precedent); 8.1's XOR constraint follows the same double-enforcement.
- **TextChoices vocabularies** held on the model (6.1 D1) — `ReportReason`/`ReportStatus` per 08 §3.2.
- **Redis via Django cache framework, never raw clients** (6.2 D3, 7.2) — the MD5 debounce keys go through the cache framework with explicit TTL.

### Integration Points
- `config/urls.py` — new `apps.moderation.urls` include under `/api/v1/` (the `/api/v1/reports/` route; `04 §52`-style cross-app prefix reuse).
- `apps/community/views.py` + `views_services.py` — the scanner call sites: post create/edit and comment create/edit (D4/D5). Caution: 5.2's two HIGH defects live in this file area (`feed_queryset` missing `is_deleted` filter; missing post-create throttle) — 8.1 must not depend on or mask them.
- `apps/accounts` — `User.is_verified`/`is_active` gate the reporter; `settings.AUTH_USER_MODEL` FKs per 08 §3.2.
- `config/settings/base.py` — `MODERATION`-related throttle rates (`MODERATION_THROTTLE_RATE` style, read at call time per project convention) and the Redis cache backend already configured for the debounce.

<specifics>
## Specific Ideas

- The block response should be polite and actionable for honest users: name the category (fee solicitation, credential request), never the pattern. This was an explicit user choice (D2) against echoing `matched_pattern`.
- The user explicitly chose spec-literal code constants over settings-held patterns (D7), accepting deploy-gated tuning — worth remembering when false positives surface in practice.
- No specific UI/mockup requirements — frontend is Phase 9. The 400 category message is the only "UX" surface in 8.1.

</specifics>

## Deferred Ideas

- **Admin-editable scam patterns** (user raised choosing to defer admin-editable to 8.2): making the four SCAM_PATTERNS editable from Django Admin instead of code constants. If wanted, it's a roadmap edit before 8.2 planning, not a discuss-phase artifact.
