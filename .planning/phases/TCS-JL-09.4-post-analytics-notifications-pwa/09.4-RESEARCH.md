# Phase 9.4 — Technical Research

**Researched:** 2026-09-24 · Scope: post detail UI over a live API, analytics aggregate, notification center UI, PWA + full background push (D2).

## R1 — The push chain already exists; D2 is an adapter, not a pipeline (biggest finding)

6.2 shipped the **entire backend push pipeline**: `create_notification()` (self-action
suppression, `transaction.on_commit`) → Celery `notifications.tasks.send_push_notification`
(retry/backoff, queue `notifications`, 15-min thread debounce D3) → `PushBackend` seam →
`FirebasePushBackend` (prod) / `RecordingPushBackend` (test). The payload already carries
**deep-link data** — `click_action: "/community/posts/{id}"` or `/dashboard` (tasks.py
`data_payload`). Zero-PII lock-screen text is template-owned (D5). `notify_comment_created`
already fires from `apps/community/services.py` on comments.

**Consequence for D2 ("full background push now"):** the browser-standards path is
**VAPID/Web Push**, and 6.2 deliberately built FCM (`firebase-admin==7.6.0`,
`Device.fcm_token`, `PUSH_BACKEND=firebase|recording|auto` in base.py:365). Options:

- **Chosen: add a `WebPushBackend` (pywebpush) implementing the existing `PushBackend`
  seam**, selected via `PUSH_BACKEND=webpush`, alongside the FCM adapter. Token storage:
  the subscription endpoint JSON is opaque like an FCM token → store it in `fcm_token`
  (TextField, unique) with `device_type=WEB`, avoiding a migration on 6.2's schema;
  `send()` maps `SendResult` semantics (410 → invalid_tokens). pywebpush (~1.0.x,
  stable, `cryptography` dep) is the only new backend dep.
- Rejected: replacing FCM wholesale (6.2's prod path is contract-tested; Android/iOS
  devices still route FCM); pyfcm-style third-party web-push wrappers (thin enough not
  to need one).
- VAPID keys: `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` env, read in
  `WebPushBackend.__init__`; absent keys in dev → auto fallback to recording backend
  (mirrors 6.2's credential-free dev posture).

**Frontend subscription:** `PushManager.subscribe({userVisibleOnly: true, applicationServerKey})`
after the §10.1 primer modal → `POST /api/v1/devices/` with the base64url endpoint key in
`fcm_token`, `device_type: "WEB"` (write serializer already accepts both fields;
upsert-by-token path already exists via `register_device`).

**SW handlers:** `push` → `showNotification(title, {body, data: {click_action}})` (the
zero-PII template text arrives in the message); `notificationclick` →
`clients.openWindow(data.click_action)` — the deep-link half of the done-when already
exists server-side.

## R2 — §7.9 needs less new backend than discuss assumed; D1 aggregate = one filtered status-distribution endpoint

`/analytics/overview/` already returns the four KPI numbers (total/waiting/JL/joined),
**both wait-time metrics with avg/median/min/max/sample-size** (7.2 D-14 rides them on the
overview payload), and suppression everywhere. `batches|hiring-types|regions` return
per-group rows with per-stream waiting/JL counts and row-floor rules (7.2 D-01). So the
**only true gap for §7.9 is a status-distribution block that honors the page's three
filters (batch × stream × region) together** — the existing endpoints each support two.
D1's "one new aggregate" = `GET /api/v1/analytics/status-distribution/?batch=&hiring_type=&region=`
→ `{suppressed, rows: [{status, count, share}], metadata}` reusing
`check_privacy_suppression` / `apply_row_floor` / `_with_metadata` verbatim. The wait-time
section renders from `overview.wait_times` (already has the `Average {n} days (Range: a to
b days)` shape). Filters: reuse `validate_filters` (raises `InvalidAnalyticsFilter`).

## R3 — Post detail: everything is served; it's pure UI + §7.8 rules

`PostDetailView` (read AllowAny), `CommentListCreateView` (read public / write
verified+active), `CommentDetailView` (PATCH/DELETE author-or-mod) are live. 1-level
nesting enforced server-side. Feed's `PostCardSerializer`/`UpvotePill`/relative-time
helpers are directly reusable. Anonymous visitors see read-only + sign-in prompt at the
composer. Locked post → amber banner replaces composer (spec rule 4).

## R4 — Notification center: API complete, UI + bell only

6.2 endpoints: list (paginated, `unread` filter), `/{id}/read/`, `read-all/`,
`preferences/`, devices list/create/delete. `Notification.unread_count_for` exists for the
AppShell bell badge. Row click = read then navigate to `post`/`comment→post`/announcement
anchor. No backend work.

## R5 — PWA: vite-plugin-pwa for the SW shell; no icon/component libraries

`vite-plugin-pwa@1.3.0` (current) supports Vite 6 (project: ^6.0.7), TS, `generateSW`
(Workbox) mode; `registerType: "autoUpdate"`, `manifest` per §10.1 (name, short_name
`JL Tracker`, theme #4F46E5/#0F172A, display standalone, portrait, 192+512 maskable).
Offline: `workbox.runtimeCaching` for `/api/v1/timeline/` + `precache` shell; amber banner
from `navigator.onLine` + `online/offline` events (no SW dependency for the banner itself).
`navigateFallback: "/index.html"`. SPA routing is react-router — SW must not cache
`/api/*` POSTs (`method: 'GET'` only in caching strategies). **No icon library and no
component library exist or will be added** (UI-SPEC `Tool: none`); 9.4 needs zero new
frontend deps besides vite-plugin-pwa (push subscribe uses native APIs).

## R6 — i18n/copy and layout constraints

## Validation Architecture

- **Unit (pytest):** `WebPushBackend.send()` against a stubbed `pywebpush.webpush` —
  SendResult mapping, 410→invalid, missing-keys fallback; status-distribution endpoint —
  suppression (k<5), filter validation, row floor; both mirror existing
  `apps/notifications/tests/` and `apps/analytics/tests/` patterns.
- **Unit (vitest):** SW registration + subscribe flow with mocked `PushManager`;
  `notificationclick` routing table; offline banner toggle; unread-count bell badge.
- **Integration:** full chain test — `create_notification` → task → `WebPushBackend`
  (recording-mode webpush double) → assert `click_action` deep link survives to payload.
- **Manual/UAT (Nyquist probes):** Lighthouse PWA installability on the running stack;
  real browser push permission flow (granted + denied); offline reload shows amber
  banner; SW deep-link click opens post detail.
- **Backstop (from UI-SPEC):** long-text wrap, KPI stacking at 400/640px, thread indent
  collapse — held-out visual/unit tests listed in `## UI Considerations`.
