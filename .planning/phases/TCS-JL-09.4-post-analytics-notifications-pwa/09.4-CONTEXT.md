## Phase Boundary

Phase 9.4 completes the community product loop and the PWA shell — four surfaces, nothing
else (D3):

- **Post detail & discussion** (§7.8, `/community/posts/:id`): route and backend are live —
  9.4 builds the screen itself: back link, post card with the §6.8 action row, comment
  composer, threaded 1-level comments with §7.8's four rules (strict nesting, inline reply
  form with autofocus, deleted-comment placeholder, locked-post amber banner).
- **Community analytics** (§7.9, `/analytics`): filters, four KPI cards, stream breakdown,
  status distribution, wait-time section, privacy suppression notice — built on 7.2's API
  **plus one new aggregate endpoint** (D1).
- **Notification center** (§7.10, `/notifications`): unread/read tabs, mark-all, row
  click→read→navigate, §7.10's empty state — UI-only over 6.2's complete API, plus the
  missing bell wire-up in AppShell.
- **PWA & push** (§10, 6.2 D16 defers the SW to here): manifest per §10.1, service worker,
  offline amber banner, §10.1's two-trigger install promotion and permission-primer modal,
  **and the full background push chain** (D2): VAPID keys, browser subscription → 6.2's
  `Device` model, Django web-push sender fired on notification create, SW
  `push`/`notificationclick` handlers deep-linking on click.

**What does NOT ship here:** settings (§7.11), moderation/reporting UI (§7.12), staff UI
(9.2 D2). §7.8's `[Reply]`/`[Report]` on comments ships Report as a real action only if a
moderation endpoint already accepts it — otherwise it is recorded as deferred, not
disabled-with-fake-reason (9.3's lesson).
