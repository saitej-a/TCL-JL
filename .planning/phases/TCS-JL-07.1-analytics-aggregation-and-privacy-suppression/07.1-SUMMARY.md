# Phase 7.1 Plan 07.1-01: Analytics Aggregation & Privacy Suppression Summary

**Phase 7.1 delivered the read-only analytics service layer the 7.2 endpoints will serve: cohort aggregations by batch, hiring stream and region, a wait-time engine with a four-step milestone fallback chain, and the mandatory `<5` candidate privacy suppression that gates every one of them.**

## Performance

- **Duration:** ~35 min
- **Completed:** 2026-09-22
- **Tasks:** 4 (all complete)
- **Suite Status:** 606 passed (584 pre-existing + 22 new), 0 failures; `ruff check apps config` clean; `ruff format --check apps config` 146 files formatted; `makemigrations --check --dry-run` → "No changes detected"; live drill 16/16.

## Accomplishments

- **Read-only app boundary (D3):** `apps.analytics` ships with no `models.py`, no `migrations/`, no `views.py`/`urls.py`/`serializers.py`, no `tasks.py` and no cache import — registered as `AnalyticsConfig` in `INSTALLED_APPS` and pinned by `test_phase_boundary.py`, which also asserts the app config registers zero models.
- **Cohort aggregation (ANAL-01/02 seam):** `get_community_overview_stats` (totals tracked/waiting/JL-reported/joined), `get_batch_breakdown`, `get_hiring_type_breakdown` and `get_region_breakdown`, each accepting the filters 04 §49 documents (`hiring_type`, `region`, `batch`) and returning the spec's own payload keys.
- **Wait-time engine (ANAL-03):** `calculate_wait_time_metrics` resolves the earliest OFFER_LETTER event, falls back to the earliest INTERVIEW event, then to `CandidateProfile.offer_letter_date`, then `interview_date`, against the candidate's earliest JOINING_LETTER event; returns `average_days` (1 dp), `median_days` (1 dp), `min_days`, `max_days` and `sample_size`; candidates whose JL precedes their baseline are excluded from the sample.
- **Privacy suppression (ANAL-04):** `check_privacy_suppression(count)` reads `settings.ANALYTICS_MIN_COHORT_SIZE` (5, unchanged from 4.2) and returns `(True, payload)` below it; every aggregation helper and the wait-time sample route through it, so a below-floor cohort yields `{data_source, suppressed, message, disclaimer}` and nothing else.
- **Attribution (D4):** every payload — suppressed or not — carries `data_source: "COMMUNITY_REPORTED"` and the 01 §48 non-affiliation disclaimer; `test_phase_boundary.py` asserts the pair is present even for a 0-candidate cohort.
- **Live Proof:** `drill_07_01.py` seeded 9 profiles across two regions, three batches and three hiring streams on the real dev database and passed **16/16** checks — overview deltas, per-batch/per-stream/per-region rows, slice suppression, the exact 4-suppressed/5-allowed boundary, the four-step wait-time chain, and a cleanup that restored the database to its exact baseline (21/21 candidates, 66/66 events).

## Deviations from Plan

None on scope. The plan's Task 2/3 helper list, Task 4 artifacts and `<verification>` commands were all delivered as written; the only deviations are the auto-fixed issues below.

### Auto-fixed Issues

1. **A hand-built date in the happy-path wait-time test overflowed January.** `test_wait_time_offer_to_jl_happy_path` constructed joining-letter dates as `date(2026, 1, 1 + days)`, which raises `ValueError: day is out of range for month` at the 40- and 50-day cases — so the only test exercising the fullest sample in the file failed before it ever asserted a statistic. Replaced with `base + timedelta(days=days)`.
2. **Ruff was red on the new module (9 findings).** `services.py` carried unused imports (`Decimal`, `Avg`, `Max`, `Min`, `Q`) and three E501 overruns; `test_aggregation_engine.py` had one. Fixed, then `ruff format apps/analytics` was applied; `ruff check` and `ruff format --check` are now clean across `apps` and `config`.
3. **The plan's named artifact `test_privacy_suppression_below_threshold` did not exist.** The suite covered the same boundary under three other names, so the plan's `<contains>` contract could not be verified. Added a test under that exact name that exercises threshold−1 (4 candidates) against all four aggregation helpers at once, then re-asserts that adding the 5th un-suppresses.

## Findings the plan could not have anticipated

- **ANAL-03's literal baseline disagrees with the locked D1 chain (open).** The requirement reads "average wait times between **survey submission** and joining letter issuance"; D1 starts the clock at OFFER_LETTER and never reads a READINESS_SURVEY event. The code follows D1 (as planned and reviewed), so this is recorded rather than resolved — recorded in `REQUIREMENTS.md` as Partial and in `STATE.md` Pending Todos. Someone must either confirm the offer-letter baseline is the intended product meaning or add the survey event as a lowest-priority 7.2 fallback.
- **Suppression is applied to the slice total, not per result row (open).** A 200-candidate national slice can therefore emit a batch row reporting 3 candidates — exactly the differential-inference vector 4.2's residual-risk note named. D2's own wording ("Sub-breakdowns … are never zeroed or partially revealed") argues for per-row floors; the locked plan's acceptance criteria only required slice-level suppression, so the stronger rule is left as an explicit decision for 7.2 rather than silently changing the payload contract the endpoints are about to be built on.
- **4.2's F2 question now has teeth.** The aggregations read `CandidateProfile` directly, so the F1 retention issue (deleted accounts keep their profile row) means anonymized-but-present candidates are counted in every cohort the public API will soon serve.
- **Each aggregation costs O(buckets) queries** — one `values(...).annotate(Count)` pass plus one status-count query per bucket — rather than a single grouped query. Fine at MVP scale and correct, but it is the reason 7.2's Redis warmup matters, and it is not covered by the project's existing query-budget-as-tests convention (COMM-08).
- **No GSD CLI verb can resolve any phase directory in this repository.** `project_code` is `TCS-JL`, and `gsd-core`'s directory grammar (`/^([A-Z][A-Z0-9_]*)-(\d.*)/`) only accepts a single-segment code, so `extractPhaseToken('TCS-JL-07.1-…')` returns the whole directory name and `query init.execute-phase 7.1`, `query find-phase 7.1` and `query phase-plan-index 7.1` all report no plans (`phase_found: true`, `phase_dir: null`, `plan_count: 0`) for **every** phase, including the already-executed 1.1–6.2. This run therefore followed `execute-phase.md` inline — plan discovery, gates and tracking updates done by hand from the plan file — and the standard wave/worktree machinery was not usable. Fixing it (rename phase dirs, or change `project_code`) is a repository-wide decision.
