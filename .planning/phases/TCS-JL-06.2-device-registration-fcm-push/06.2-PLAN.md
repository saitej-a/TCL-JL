## Planner resolutions (06.2-CONTEXT.md open questions 1–4 + integration details)

- **R1 — TIMELINE_REMINDER stays producer-less through v1 (open question 1).** Evidence: `config/celery.py`'s beat holds exactly three entries (device prune, announcement cleanup, analytics warmup) and no roadmap phase claims a reminder producer. The type, its `notify_timeline_reminders` flag, and the task's D14 gate mapping all ship, so a future producer lands with zero changes here. The boundary test asserts no producer exists; the SUMMARY records where one would land (a maintenance-queue beat task, own phase decision).
- **R2 — No multicast batch loop in 6.2 (open question 2).** With announcements deferred (D15), every push fans out to **one recipient's** devices; the 10/hour registration throttle bounds a user's device count far below the SDK's 500-token `send_each_for_multicast` ceiling. Tests assert the full token list in a single multicast call. Phase 8's broadcast owns batching (07 §5.2's 500-chunk pattern).
- **R3 — Preferences contract (open question 3).** `GET /api/v1/notifications/preferences/` returns 200 with all six flags plus `created_at`/`updated_at` (read-only); the row is created on first read via `get_or_create_for` (R6's sanctioned accessor — a read with a lazy-write side effect, documented). `PATCH` is partial: any subset of the six booleans, 200 with the full updated shape; non-boolean values are DRF 400 field errors; unknown keys are ignored (DRF default — consistent with 5.2's write serializers). No id in the URL (D13).
- **R4 — Retry ladder (open question 4).** Decorator keeps §5.1's shape with a pinned base: `autoretry_for=(Exception,), max_retries=3, retry_backoff=2, retry_backoff_max=60` → Celery yields jittered exponential delays ≈2s/4s/8s, capped at 60s. This is a **documented approximation of §12's illustrative 2s/8s/32s** — Celery's backoff formula cannot express that exact ladder, the resilience property (bounded, exponential, capped, isolated) is identical, and jitter is what protects FCM from a synchronized retry herd after an outage. After exhaustion the task logs `PUSH_DELIVERY_EXHAUSTED` (notification_id, type) and ends — no dead-letter queue in v1 (§13's counters are logs; Phase 10.2 owns observability). The in-app row is untouched; §12's isolation boundary holds by construction.
- **R5 — Enqueue kwargs.** `create_notification(..., push_context=None)` forwards its dict as task kwargs on commit: `send_push_notification.delay(str(id), **push_context)`. v1 defines exactly one key: `count` (the crossed milestone threshold), so the VOTE_MILESTONE push template needs no parsing of stored text and cannot drift from the milestone actually crossed.
- **R6 — D9's internal tension resolved: GET /devices/ writes nothing.** D9 lists POST and GET as last_seen endpoints but also mandates "no write on hot read paths" — and with no device-identity header (rejected), a GET cannot attribute itself to a row; bumping *every* row would falsify all of them. Pin: POST /devices/ moves the affected row's `last_seen_at` (saved with `update_fields` naming it — 6.1 R9's caveat); GET is read-only. "Last seen" therefore means "last registration/reassignment of that token", which is exactly what §7.1's settings copy shows.
- **R7 — Throttles.** `device_registration: "10/hour"` on POST /devices/ (§10). `notifications_reads: "60/min"` on the two list GETs (the pollable hot paths). Mark-read/read-all/PATCH preferences stay unthrottled — idempotent, low-value targets; same accepted-risk posture as 5.2's comment-create note, revisited at Phase 8/10.
- **R8 — Route hygiene.** pk converters are `<str:pk>` + a `_clean_uuid`-style parse (community's F3 discipline) so malformed UUIDs 404 inside the project envelope. Preference routes are declared before parameterized ones. All views run `IsAuthenticated + IsActive + IsVerified` and the `SpecErrorMixin` chain so 401/429 render the project envelopes.
- **R9 — `updated_at` on bulk deactivation.** `QuerySet.update()` bypasses `auto_now` entirely, so the task's stale-token deactivation passes `updated_at=timezone.now()` explicitly (07 §5.1's own pattern) — the 30-day prune reads `updated_at`, and R6 keeps `last_seen_at` out of that write.
- **R10 — Test matrix** below (~95 tests; suite 486 → ~580), mapped onto 07 §14's five prescribed files.

## Scope note (one plan, six tasks — deliberate)

`06.2` covers two roadmap plans (`06-02` + `06-03`) in one execution unit, exactly as 5.2 did for `05-02`+`05-03`: the device/notification endpoints, the push pipeline, and the producers share the same service module and the same spec surface, and splitting them would orphan the enqueue path (a producer without a task, or a task without a producer). Task order is dependency order: seam → service → device API → notification API → tasks → producers → proof; each task's tests run before the next begins. No task depends on another plan; `wave: 1`, `depends_on: []`.
