## FCM boundary & delivery policy

### Q1 — Which Firebase integration, and how heavy a dependency?

| Option | Description | Selected |
|--------|-------------|----------|
| firebase-admin + sender seam | The spec's SDK behind a `PushBackend` setting; recording backend for unconfigured/CI environments. First new dependency since Phase 1; pulls grpc/Firestore/Storage transitively. | ✓ |
| pyfcm (light HTTP v1) | One light dep (`requests`), HTTP v1 via service account; not the spec's SDK, and multicast batching plus per-token error classification become ours. | |
| Raw HTTP v1 + google-auth | No FCM SDK; most control, most code to own (token caching, 500-token cap, error mapping, backoff). | |
| You decide | Let Claude choose and record the reasoning. | |

**User's choice:** firebase-admin + sender seam.
**Notes:** Accepted the transitive dependency weight in exchange for the spec's SDK and the seam's credential-free testability.

### Q2 — How far does the real Firebase side go in 6.2?

| Option | Description | Selected |
|--------|-------------|----------|
| Real adapter now, verified credential-free | `FirebasePushBackend` ships; unit tests assert the `MulticastMessage`, the recording backend asserts task decisions; no live FCM call. | ✓ |
| Seam now, real SDK in Phase 10.2 | Defer `firebase-admin` entirely until launch readiness, when credentials exist. | |
| Real adapter + opt-in live probe | Same as recommended plus a scripted real send when credentials and a token are supplied. | |

**User's choice:** Real adapter now, verified credential-free.
**Notes:** The phase must not claim end-to-end push verification; only the message we hand the SDK is proven.

### Q3 — What does the 15-minute debounce do to later pushes in the window?

| Option | Description | Selected |
|--------|-------------|----------|
| Suppress, non-thread types exempt | In-app rows always created; `cache.add(key, 1, timeout=900)` on the cache framework; ANNOUNCEMENT/SYSTEM/TIMELINE_REMINDER bypass because a post-less key collides. | ✓ |
| Coalesce into one summary push | Count suppressed events, send one "N new comments" at window expiry. | |
| Suppress, arm only after a successful send | Same suppression, key set post-delivery so a failed send does not lock out its own retry. | |

**User's choice:** Suppress, non-thread types exempt.
**Notes:** VOTE_MILESTONE was added to the exemption list during Q4, since it carries a `post_id` and would otherwise be swallowed by a comment push in the same window.

### Q4 — Milestone triggering and double-fire prevention

| Option | Description | Selected |
|--------|-------------|----------|
| Threshold watermark, no schema change | Settings-held thresholds; pre/post-insert count comparison; watermark = count of existing VOTE_MILESTONE rows for the post. | ✓ |
| Exact crossing only, no dedupe | Smallest rule; an unvote/re-vote toggle across a threshold re-notifies every cycle. | |
| Add a milestone_threshold column | Explicit dedupe, optionally a UniqueConstraint; costs a migration in a phase expected to be model-stable. | |

**User's choice:** Threshold watermark, no schema change.
**Notes:** Two consequences recorded in CONTEXT: editing the thresholds list later shifts watermark indices, and a threshold crossed by the author's own vote is never reported.

## Device API semantics

### Q1 — A POST /devices/ arrives with a token belonging to another user

| Option | Description | Selected |
|--------|-------------|----------|
| Reassign to the caller | Last-writer-wins; the token identifies a browser, and possession is the only way to reach this branch. | ✓ |
| Refuse with 409 token_owned_elsewhere | Spec-literal §8.3 reading; breaks shared-browser account switching permanently. | |
| Hybrid: reassign only if the old row is inactive | Strictest reading with a narrow handover escape hatch; degenerates to 409 in the common case. | |

**User's choice:** Reassign to the caller.

### Q2 — Does a revoked device row survive, and what does the list show?

| Option | Description | Selected |
|--------|-------------|----------|
| Soft deactivate, list shows active only | `is_active=False` + 204; the daily prune cron stays the single row deleter; list filters to active. | ✓ |
| Hard delete the row | One removal path; two different durabilities across writers and lost `created_at` history. | |
| Soft deactivate, list shows inactive too | Mirrors §11.5's payload with `is_active` visible; noisier list and an extra state for 9.4 to render. | |

**User's choice:** Soft deactivate, list shows active only.

### Q3 — Shape of GET /api/v1/devices/

| Option | Description | Selected |
|--------|-------------|----------|
| Default DRF pagination envelope | `count`/`next`/`previous`/`results` at PAGE_SIZE 20, like every other list endpoint. | ✓ |
| Flat results array as literally specified | Byte-for-byte §11.5; the only unpaginated list in the API, unbounded. | |
| Flat array, hard-capped | Spec shape with a silent truncation the client cannot detect. | |

**User's choice:** Default DRF pagination envelope.

### Q4 — Which requests refresh last_seen_at

| Option | Description | Selected |
|--------|-------------|----------|
| Device endpoints only | Moves on register/list; no new client header, no writes on hot paths, pruning keeps using `updated_at`. | ✓ |
| Every authenticated request from that device | Needs an `X-Device-Id` header and middleware; a DB write on essentially every API call for a cosmetic timestamp. | |
| Device endpoints plus a throttled heartbeat | Closer to real activity, with a stateful window depending on which endpoints the client polls. | |

**User's choice:** Device endpoints only.
**Notes:** A token-refresh write must name `last_seen_at` in `update_fields` (6.1 R9).

## Notification creation & suppression

### Q1 — How community writes reach the notification layer

| Option | Description | Selected |
|--------|-------------|----------|
| Explicit service calls | `create_comment` and `vote_post` call the notifications service; the seam 5.2 P12 documented. | ✓ |
| Django post_save signals | Fully decoupled, but implicit, hard to order, and silently double-notifies on re-saves and seed paths. | |
| Hybrid: signals for comments, explicit for milestones | Covers both failure modes; two mechanisms for one feature. | |

**User's choice:** Explicit service calls.
**Notes:** The `# Phase 6 hook:` comment 5.2's plan promised is absent from the code; both call sites must gain it.

### Q2 — Transaction boundary for the row and the enqueue

| Option | Description | Selected |
|--------|-------------|----------|
| Row in-transaction, delay() on commit | Row atomic with the comment; enqueue after commit so the worker never sees an uncommitted row (§5.1 discards missing notifications). | ✓ |
| Row and delay() both inline | Literal §5 diagram; a fast worker can discard the push and a broker outage raises inside the request. | |
| Everything on commit, row included | Comment can never fail for a notification reason, but a crash between commit and callback loses the row permanently. | |

**User's choice:** Row in-transaction, delay() on commit.

### Q3 — Which text goes into the FCM payload

| Option | Description | Selected |
|--------|-------------|----------|
| Rich row, generic push template | Row keeps §4.1's in-app text with the preview; the task composes the lock-screen body from per-type templates; no comment body reaches FCM. | ✓ |
| One push-safe text everywhere | §5.1's code path unchanged; the bell reads the same generic sentence for every comment. | |
| Store both texts on the row | Cleanest separation; a migration for derivable data. | |

**User's choice:** Rich row, generic push template.
**Notes:** Deliberate deviation from 07 §5.1's sample code, which sends the stored row text.

### Q4 — Author's own vote crossing a milestone

| Option | Description | Selected |
|--------|-------------|----------|
| Suppress it | §10's "zero self-notifications" is absolute; the watermark still reports the next threshold and blocks re-crossings. | ✓ |
| Exempt milestones from self-suppression | Reads naturally for a post achievement; contradicts §10 and notifies the user about their own click. | |

**User's choice:** Suppress it.

## Claude's Discretion

Delegated by the user and recorded in CONTEXT.md so the planner does not re-ask:

- **Dashboard wiring** — `apps/timeline/services.py:212` calls `unread_count_for(request.user)`, and the notification list exposes the unread count for the client badge.
- **Throttle scopes** — a `device_registration` scope at 10/hour (§10), plus a read scope for the notification endpoints, using the existing `ScopedRateThrottle` + `DEFAULT_THROTTLE_RATES` pattern.
- **IDOR** — 404 for foreign devices and notifications (§11.2, 4.2's precedent).
- **Mark-all-read** — one UPDATE writing both `is_read` and `read_at` (6.1 D5), reporting `updated_count`.
- **Telemetry** — §13's metrics as structured log lines; no metrics stack in 6.2.
- **Ordering/filtering** — the model's pinned `-created_at`, with `?is_read=false` walking `idx_notif_recip_read_created` and the count staying `unread_count_for`.
