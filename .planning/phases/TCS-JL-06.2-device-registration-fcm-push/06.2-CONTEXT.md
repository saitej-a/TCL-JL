<decisions>
## Implementation Decisions

### FCM integration & the dependency boundary

- **D1 — `firebase-admin` behind a `PushBackend` seam.** 07 §6 names the authoritative SDK and
  the HTTP v1 API; 6.2 adopts it as the **first new dependency since Phase 1**. It is wrapped:
  a settings-selected backend (`firebase` when credentials/adc are available, otherwise a
  recording backend) so nothing about the tests, CI, or a fresh checkout depends on a live
  Firebase project. Accepted cost, recorded deliberately: `firebase-admin` brings
  `google-api-core[grpc]`, Firestore and Storage transitively for a messaging-only need.
  Rejected: `pyfcm` (lighter, but not the spec's SDK and it leaves per-token error classes to
  us), raw HTTP v1 + `google-auth` (fewest deps, most code we then own).
- **D2 — The real adapter ships now and is verified credential-free.** `FirebasePushBackend`
  is real code in 6.2 (build the `MulticastMessage`, call `send_each_for_multicast`, classify
  `UnregisteredError` / `SenderIdMismatchError` per token). Verification is: unit tests assert
  **the exact message handed to the SDK** (tokens, title, body, data keys, webpush link), and
  the recording backend asserts the task's *decisions* (who was skipped and why). No live FCM
  call happens in this phase, so the phase must not claim end-to-end push verification.

### Push delivery policy

- **D3 — The 15-minute debounce suppresses, and only thread pushes are debounced.** Key
  `debounce_push_post_{recipient_id}_{post_id}`, armed with `cache.add(key, 1, timeout=900)`
  **through Django's cache framework** (never a raw redis client) — which keeps the tests on
  `LocMemCache` per `config.settings.test` and needs no Redis to run. The in-app row is created
  regardless. **Exempt:** `ANNOUNCEMENT`, `SYSTEM`, `TIMELINE_REMINDER` (no `post_id`, so a
  naive key collides across unrelated announcements and would silently drop them) **and
  `VOTE_MILESTONE`** (it carries a `post_id` and would otherwise be swallowed by a comment
  push in the same window). Rejected: coalescing into a summary push (needs a counter plus a
  delayed follow-up task, and can deliver stale summaries).
- **D4 — Milestones are settings-held with a count watermark, and a self-crossing is
  suppressed.** `VOTE_MILESTONE_THRESHOLDS = [10, 25, 50, 100, 250, 500]` in
  `config/settings/base.py`, read at call time (the `BATCH_YEARS` / `TRENDING_WINDOW_DAYS`
  precedent, so ops can tune without a deploy). The hook compares the pre-insert and
  post-insert vote counts to find the newly crossed threshold, and dedupes by comparing the
  crossed threshold's index against the number of `VOTE_MILESTONE` rows that post already has —
  so vote toggling cannot re-notify, and no migration is needed. When the author's own upvote
  is the crossing vote, the notification is **suppressed** (§10's "zero self-notifications" is
  absolute); the watermark still lets the next threshold report correctly.
  **Two caveats for the planner to write down:** the watermark means "how many milestone rows
  this post has", so *editing* the thresholds list later shifts indices; and a threshold that
  was suppressed because the author crossed it themselves is never reported.
- **D5 — The row keeps the rich in-app text; the push body comes from a per-type template.**
  07 §4.1.1–§4.1.4 give separate in-app and push texts, and §5.1's sample code wrongly sends the
  stored row text to FCM (which would put every comment preview on a lock screen and contradict
  §8). So: the stored `title`/`message` are the in-app texts (§4.1's `display_name` + post
  title + preview, composed per 6.1 D3/D4), and the Celery task composes the lock-screen body
  from a fixed per-type template table. **No comment body can ever reach FCM**, which makes §8's
  rule structural rather than a truncation heuristic. `07 §5.1`'s sample is deviated from
  deliberately. Rejected: one push-safe text everywhere (the bell would read "Someone commented
  on your post" for every row), and storing a second `push_body` column (a migration for
  derivable data).

### Device API semantics

- **D6 — A token already bound to another user is reassigned to the caller (last-writer-wins).**
  An FCM token identifies a *browser*, not a person, so on a shared machine the second candidate
  to log in would otherwise never receive push on that browser. The token is never exposed by the
  API (`write_only`, never logged — 6.1 R3/T-6.1-01), so possession is the only route into this
  branch; §8.3's intent ("no registering devices on behalf of another account") is preserved
  because you can only ever attach a token you possess. The row's `user`, `is_active`,
  `browser` and `device_type` are updated; the previous owner recovers by re-registering.
  Rejected: `409 token_owned_elsewhere` (breaks shared-browser switching permanently) and the
  hybrid "only when the old row is inactive" (which degenerates to the 409 in the common case
  while adding a state-dependent branch).
- **D7 — Revoke is a soft deactivate; the device list shows active rows only.**
  `DELETE /api/v1/devices/{id}/` sets `is_active=False` (with `updated_at`) and returns **204**;
  the row survives so the already-scheduled daily `prune_stale_devices` task remains the **single
  place** device rows are deleted. One state machine with two writers (user revoke, FCM
  `UnregisteredError`) and one reaper. `GET /api/v1/devices/` filters to active rows, so a
  revoked browser reads as gone to the user. Rejected: hard delete (two removal paths with
  different durability, lost `created_at` history on re-register) and showing inactive rows.
- **D8 — `GET /api/v1/devices/` uses the default DRF pagination envelope.**
  `count`/`next`/`previous`/`results` at `PAGE_SIZE = 20`, like every other list endpoint in the
  project (feed, comments, timeline, notifications). §11.5's bare `results` array is treated as
  illustrative of the *item* shape, not the envelope.
- **D9 — `last_seen_at` moves on device endpoints only** (`POST /devices/`, `GET /devices/`).
  No `X-Device-Id` header and no middleware, so there is no write on hot read paths and no new
  client contract. Documented consequence: "last seen" means *last device interaction*, not last
  authenticated request. **A token-refresh write must name `last_seen_at` in `update_fields`** —
  6.1 R9 pins that `auto_now` does not fire for excluded fields. Pruning keeps using
  `updated_at` per §7.2.

### Notification creation & suppression

- **D10 — Explicit service calls, not signals.** `community.services.create_comment` (line 95)
  and `community.views_services.vote_post` (line 132) call a notifications service after their
  own write. 5.2 P12 documented exactly this hand-off (and planned a `# Phase 6 hook:` comment
  that is **not actually in the code** — both call sites must gain it). Signals were rejected
  again here for the reasons 5.1/5.2 and 6.1 R6 already recorded: implicit ordering, silent
  double-notification on re-saves and bulk/seed paths.
- **D11 — The row is written inside the request transaction; `.delay()` runs on commit.** A
  rolled-back comment can never leave an orphan notification, and the worker can never pick up a
  task whose row is not yet visible — that race is real, because 07 §5.1's own task body logs
  "Notification does not exist; discarding task" and returns, silently losing the push. Enqueue
  via `transaction.on_commit`. The push stays asynchronous, so §12's failure boundary holds: an
  FCM or broker outage can never roll back a candidate's comment or timeline update.
- **D12 — Recipients and self-action suppression follow §4 exactly.** `COMMENT` → the post
  author; `REPLY` → the **parent comment's** author (not also the post author — one row per
  event, no duplicate bell entries); `VOTE_MILESTONE` → the post author. Each is suppressed when
  the actor *is* the recipient (`§4.1.1`/`§4.1.2`'s explicit rules plus D4's milestone rule).
  §4's `ANNOUNCEMENT` recipient rule ("all active registered candidates") is deferred with D15.

### Preferences

- **D13 — 6.2 ships `GET` + `PATCH /api/v1/notifications/preferences/`.** NOTIF-06 requires
  candidates to manage preferences; 07 §11 defines no such endpoint, and 6.1 shipped only the
  model plus `get_or_create_for`. The endpoint is small, owner-scoped with **no id in the URL**
  (so no IDOR surface), uses `get_or_create_for` as the single accessor, and closes NOTIF-06
  inside the phase that owns it. Without it 6.2 would ship a push task honouring six flags no
  user can change.
- **D14 — The flags gate the push only, and cover every type.** Rows are always created (the bell
  is the record of what happened) — literally §3.3's own words, "which event categories dispatch
  external push notifications versus remaining silent in-app alerts". The task's mapping is
  complete: `COMMENT`/`REPLY`/`VOTE_MILESTONE`/`ANNOUNCEMENT`/`TIMELINE_REMINDER` to their own
  flags, and `MODERATION`/`SYSTEM` gated by `push_enabled` alone (operational alerts with no
  category flag). This fixes 07 §5.1's sample, which never consults
  `notify_timeline_reminders` and would push reminders to users who switched them off.

### Phase boundaries

- **D15 — Announcements are deferred to Phase 8 in full.** No `Announcement` model, no
  `broadcast_announcement` implementation, no announcement in-app fan-out; the reserved
  `notifications.tasks.broadcast_announcement` route stays inert (as it is today), and Phase 8
  owns the model, the publishing surface and `notify_on_announcements` verification. **Consequence
  the planner must state plainly:** at the end of 6.2 only **three** types have live producers
  (`COMMENT`, `REPLY`, `VOTE_MILESTONE`), which corrects 6.1 D1's "four have v1 producers" — the
  `ANNOUNCEMENT` producer arrives with Phase 8, not here. `notify_on_announcements` is exposed by
  D13's endpoint before anything honours it.
- **D16 — No service worker in 6.2; the payload contract is pinned by tests instead.** T6.12's
  `firebase-messaging-sw.js` needs a frontend, a build pipeline and the Firebase client config
  that only Phase 9.4 has. 6.2 freezes the contract 9.4 must implement — the push `data` keys
  (`notification_id`, `type`, `click_action`) and §4's deep-link shapes — with assertions in the
  push task's tests, and records the deferral so the Phase 10 launch checklist catches it rather
  than a stray file implying it is done.

### Claude's Discretion

Recorded here so the planner does not have to re-ask; the user delegated these:

- **Dashboard wiring** — `apps/timeline/services.py:212` calls
  `Notification.objects.unread_count_for(request.user)` (4.2 D1's seam, 6.1 D6's helper), and the
  notification list response exposes the unread count so the client badge needs no second call.
- **Throttle scopes** — a new `device_registration` scope at **10/hour per §10's anti-storm
  table**, plus a read scope for the notification endpoints, declared as `ScopedRateThrottle`
  subclasses with rates in `REST_FRAMEWORK["DEFAULT_THROTTLE_RATES"]` (the `auth_*` /
  `community_writes` pattern).
- **IDOR** — foreign devices and notifications return **404**, not 403 (§11.2 states it for
  notifications; 4.2 set the project-wide precedent).
- **Mark-all-read** — writes **both** `is_read` and `read_at` in one `UPDATE` (6.1 D5's
  constraint makes the pair mandatory) and reports `updated_count` per §11.3.
- **Telemetry** — §13's metrics become structured log lines through the existing logging config;
  no metrics stack ships in 6.2 (Phase 10 owns observability).
- **Ordering** — the notification list keeps the model's pinned `-created_at` (6.1 R7);
  `?is_read=false` filters through `idx_notif_recip_read_created` and the D6 count stays
  `unread_count_for`.

## Open Questions for Research

Flagged rather than decided — the researcher should resolve these with evidence:

1. **`TIMELINE_REMINDER` has no producer in any roadmap phase.** §4's matrix wants a 30-day
   inactivity reminder, but no beat entry is reserved in `config/celery.py` (only pruning,
   announcement cleanup and analytics warmup are) and no phase claims it. Confirm it stays
   producer-less through v1 and record where it would land.
2. **Is FCM's 500-token multicast cap a real constraint here?** With announcements deferred
   (D15) a single notification fans out to one recipient's devices, so batching may be
   unnecessary in 6.2 — the researcher should confirm the recorded backend needs no batch loop.
3. **The exact `GET/PATCH /api/v1/notifications/preferences/` response shape** — field names,
   whether the row is created on first read (`get_or_create_for` semantics), and PATCH's
   partial-update behaviour. §11 constrains nothing here.
4. **The Celery retry ladder in practice** — §12 says 3 attempts at 2s/8s/32s and §5.1's decorator
   uses `autoretry_for=(Exception,)` with `retry_backoff_max=60`. Confirm the effective schedule
   (backoff is exponential with jitter) and what should happen after exhaustion (drop vs a
   recorded failure).
