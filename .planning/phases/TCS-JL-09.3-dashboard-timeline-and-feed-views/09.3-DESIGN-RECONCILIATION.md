`grep -cE "\`[0-9a-f]{32}\`" 09.3-CONTEXT.md ≥ 7` — a count of *recorded* screen IDs, which cannot

the generated designs") silently did not happen for this phase: no 9.3 source file mentions Stitch,

where the mockup invents data the API does not carry, the divergence is recorded here rather than

## Second pass: the frame (after comparing the running app to the design)

The first pass compared mockup text to source and never put the rendered page beside the design.
Doing that exposed the dominant difference, and it was not a styling detail — it was a routing
mistake:

| # | Surface | Design | Was | Now |
|---|---|---|---|---|
| 23 | Whole community section | Feed sits **inside** the app frame: 240px sidebar (brand + `+ Create Post` + nav), top bar with search, 320px rail, disclaimer footer | `/community` was a top-level route with no `AppShell` — a bare column on an empty page, while every mockup showed it framed | `PublicShell` layout route mounts `/community` and `/community/posts/:id` in `AppShell`. Access control untouched (D1's anonymous read is an API property, not a layout one); the shell already degrades for visitors — email hidden, account-only links route through `/login?next=`. |
| 24 | Feed filters | Search field, pills and tabs grouped in one bordered block, search carrying its icon | Three loose elements stacked in the column | One filter card; icon inside the field |
| 25 | Feed category row | Capped pill row + `[+ More]` | All 11 categories always rendered, wrapping to two rows | Cap of five + a disclosure that reveals the rest, and a category chosen from behind the fold stays visible so the active filter is never hidden |
| 26 | Feed sort row | Segmented control: a track with the active tab raised on its own surface and a leading dot | Underlined text tabs | Segmented control, active tab raised with the dot |
| 27 | Feed rail | `MY STATUS SUMMARY` beside the feed | Rail slot empty | `RailStatusSummary` extracted from the dashboard and shared; the feed fills the rail when signed in, and skips the request entirely when anonymous |
| 28 | Page container | The shell owns the frame; the page owns only its rhythm | Page added its own `max-w-4xl p-4 lg:p-8` on top of the shell's padding | Page contributes spacing only |

Still deliberately not built on the feed, and why: the design's `LIVE FEED • Updated 2 min ago` eyebrow
(no live-refresh or updated-at exists — a painted green dot over a page that never refreshes is a
lie), the `12 new` notifications pill (unread count is not on the feed payload), category counts
(no endpoint, 9.3 D7), the pinned announcement card (no announcement in the dev database — needs
seed data to judge), and the mobile pill row's horizontal scroll (the rows wrap instead).

## Defects found while reconciling (pre-existing, all fixed)

Reading the mockups exposed three things that were wrong on their own merits — none of them
cosmetic, all of them the kind of thing a visual pass catches and a grep cannot.

1. **A successful upvote reverted to the pre-vote number.** `UpvotePill`'s docstring promises it
   "reconciles against the server's `has_voted`/`vote_count`", and the feed kept both in its
   per-card store — but `PostCard` never accepted the count, reading `post.vote_count` (the list
   fetch's stale snapshot) instead. So the optimistic increment was visible while the request was
   in flight and then *disappeared* on success. UI-03's own failure mode, inverted. `PostCard` now
   takes `count` from the store and the feed passes it.
2. **The feed's test script assumed StrictMode in the test renderer.** StrictMode lives in
   `main.tsx` only, so effects fire once; the two "StrictMode replay" steps per test meant the
   filtered request landed on the mount step and the vote POST landed on a GET. Both tests were red
   before this reconciliation and are green now (one of them, the vote test, could only pass once
   defect 1 was fixed — which is why the broken wiring survived: the script hid it).
3. **`npm run build` was failing on committed code.** `TimelinePage.handleSubmit` guarded with
   `modal?.event === null || modal.event === undefined`, which leaves `modal` unnarrowed and
   dereferences a possibly-null value on the next line; `tsc -b` (the build) rejected it while
   `npm run typecheck` (`tsc --noEmit`) did not, because the two use different configs. The target
   is now read once into a local. `npm run lint`, `typecheck`, `test:run` (28 files / 129 tests) and
   `build` are all green.

## Method note for the verify stage

The reconciliation above was done by re-reading the mockups, not by looking at the running app. The
directive's §4 still owes a side-by-side against the live `/dashboard`, `/timeline`, `/community`
and `/community/create` at ≥1280px and ≤400px, which Task 9's live-proof step covers — the checks
that matter most there are the ones a screenshot alone decides: the stepper's completed/pending
pulse states, the roadmap's three node states, the pinned card, and the card action row at narrow
widths.

The verify stage must compare the *running* app against these screens side by side and append any
new divergence here. The screenshots are reachable via `get_screen` with the IDs above; the
`htmlCode.downloadUrl` extracts cleanly for every screen **except the desktop feed**, whose HTML
text extraction returns only the pinned card — read that one from the screenshot, not the text.
