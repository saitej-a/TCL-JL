## 1. The feed is public in the SPA and private in the API

**The situation:** the SPA's route table (9.1 D9) already renders `/community` and
`/community/posts/:id` **outside** `RequireAuth`, matching 05 §3.1's access matrix ("All
(Public Read) … clicking Create, Upvote, or Comment prompts Login Modal") and 05 §7.6's
public-feed framing. The shipped backend disagrees: `PostListCreateView`,
`PostDetailView`, `CommentListCreateView` and `CommentDetailView` all carry
`permission_classes = [IsAuthenticated, IsActive, IsVerified]`, so a visitor gets a **401**
on the exact routes the SPA promises them. `apps/community/tests/test_feed_api.py` even
pins it: `test_feed_requires_authentication` asserts 401.

**Chosen:** open anonymous read (D1) — `GET` on the feed list, post detail, and comment
list/detail becomes anonymous-allowed; every write surface is untouched; anonymous callers
are rate-bounded by a read throttle whose scope is declared on the view.

**Alternatives considered:**
- *Keep the feed authenticated and move the routes under `RequireAuth`.* The smaller code
  change (frontend only), and 04 §118 explicitly calls anonymous community reading a product
  decision the API may refuse. Rejected: it contradicts 05 §3.1 and §7.6, throws away the
  login-modal affordance entirely, and makes the landing page's "Community" nav link a
  login wall — a product-visible regression booked as a rendering detail.
- *Allow anonymous reads but suppress anonymous search/filtering.* Bounds scraping harder,
  but it invents a surface neither spec describes and would need its own error contract.
  Rejected as unrequested complexity; pagination (20/page) plus the read throttle already
  bound enumeration.
- *Open reads by making `IsVerified` optional in the shared permission class.* Rejected:
  that class also guards writes; the change must be per-method, not global.

**Security note carried to planning:** the author payload is already redaction-safe
(`AuthorPublicSerializer` + tombstone masking), so anonymous reading exposes no PII; the new
anonymous surface is bounded by pagination + throttle and adds no write path. The existing
401 test is **updated deliberately** (it encodes the old contract), with the change recorded
in its docstring — the 9.2 precedent.

## 2. Backend gaps 9.3's own feed depends on

**The situation:** the phase's views sit on top of community surfaces that are broken,
missing, or decorative in the live tree. Presented as a multi-select: which belong inside
9.3 rather than being worked around in the client?

**Chosen (3 of 4):**
- **Deleted posts leak into the feed** (D2). `feed_queryset` never filters
  `is_deleted=False` while `trending_queryset` does, so soft-deleted posts still appear in
  the default feed and in `?search=` — the exact 05.2 F1 HIGH defect, re-confirmed in the
  current tree. Fixed here because 9.3 *is* the feed.
- **The vote response carries no own-state flag** (D3). `VoteSerializer` returns
  `{id, vote_count, is_pinned, is_locked}`; the optimistic pill cannot read back what it
  just changed, so "did my vote land?" would be answered purely by the client's own
  optimism. Fixed here because UI-03 is the phase's requirement.
- **Community write throttling cannot engage** (D4). `PostListCreateView` declares no
  `throttle_classes` (05.2 F2) and none of the seven views that attach
  `CommunityWriteRateThrottle` declares `throttle_scope`, so DRF allows every request
  (7.2 R1's discovery). Fixed here because 9.3 ships the write UI that the limit was
  supposed to bound.

**Deliberately declined (and recorded):** the missing `GET /posts/categories/` endpoint.
04's endpoint inventory lists it and `settings/base.py:169` claims it exists, but no view,
route, or test ships. Consequence is **D7**: the 12 keys are held in one frontend constant
module with a test pinning the exact set — a deliberate duplication of a settings-held
vocabulary, to be reclaimed when the endpoint ships.

**Alternatives considered for the declined piece:** *invent the endpoint anyway* (a
read-only route over `settings.POST_CATEGORIES` — cheap, removes the duplication, but it is
new API surface the phase was not scoped for) and *hardcode the pills inline in the feed
component* (worst: the vocabulary would then be editable in two files with no test pinning
either). The endpoint-to-backlog route was chosen; the constant module keeps the duplication
in exactly one place.

## 3. How far 9.3 reaches

**The situation:** the roadmap assigns 09-03 = dashboard + timeline + feed and 09-04 = post
detail + comments + analytics + notifications + PWA. §7.7 create post is assigned to
**neither**, yet both feed CTAs target `/community/create`. Separately, §7.4's "Latest
discussions in your stream" block has no backing filter: posts carry a `category`, and the
hiring stream lives on the *author's* profile, so the feed endpoint cannot filter by it.

**Chosen:** create post ships in 9.3 (D5), and the dashboard block shows the community's
newest posts (D6), with the divergence recorded rather than papered over.

**Alternatives considered:**
- *Give §7.7 to 9.4, ship a read-only feed now.* Keeps 09-04's title intact, but leaves the
  feed's primary CTA and its empty state both pointing at a stub for a whole phase. Rejected.
- *Add a hiring-stream query parameter to the feed endpoint.* The dashboard block would be
  genuinely "in your stream". Rejected for this phase: it is new API surface, it changes the
  feed's cache/pagination contract, and the block is a dashboard nicety — recorded as a
  divergence so it can be bought deliberately later.
- *Drop the block entirely.* Removes a §7.4 widget the mockups show. Rejected.

## Findings surfaced during the discussion (not decisions)

1. **Route table vs API disagree on feed visibility** — `/community` is public in the router
   and auth-required in the backend (D1).
2. **`test_deleted_posts_absent_from_feed` is vacuous** — it asserts a literal title is
   absent from a list of *masked* titles, so it passes whether or not deleted posts leak (D2).
3. **`PostListCreateView` has no `throttle_classes`; no write view declares `throttle_scope`**
   — 04 §41/§42's write limits allow every request today (D4).
4. **`VoteSerializer` has no own-state flag** (D3).
5. **`GET /posts/categories/` does not exist** despite 04's inventory and a settings comment
   asserting that "5.2's endpoint serves these same keys + labels" (D7).
6. **`ToastProvider` is not mounted** — `App.tsx` composes ErrorBoundary → ThemeProvider →
   AuthProvider → RouterProvider, so `useToast()` throws anywhere it is used; §6.8's
   rollback-with-toast needs the provider in the tree.
7. **`avatar_seed` is the server's palette index**, not a client-computed colour: 5.2 derives
   it with an HMAC over the candidate id and exposes only the index (D-consumption rule:
   consume, never recompute).
