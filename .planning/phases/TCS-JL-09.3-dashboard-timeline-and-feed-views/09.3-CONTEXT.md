<domain>
## Phase Boundary

Phase 9.3 turns 9.2's authenticated chrome into the three views that carry the product's core
loop — see your progress, maintain your own record, and read the community:

- **Candidate dashboard** (§7.4): welcome header with status + "since" date, the status
  **stepper bar**, the community benchmark card (suppressed-aware), community pulse, and the
  "latest discussions" block; the desktop right rail (a 9.2 placeholder) is filled here.
- **Personal timeline** (§7.5): the interactive vertical roadmap — completed nodes with
  dates, pending nodes with quick actions ("Mark as Received" / "Set Date"), per-node
  edit/delete, and the add/edit milestone modal (§7.5's modal, with the description
  counter and the auto-status note).
- **Community feed** (§7.6): category pills, the three tabs (Latest / Trending / Top Voted),
  debounced search, the pinned announcement card, post cards with the §6.8 upvote pill, and
  pagination — with **optimistic upvoting and rollback** (UI-03, the phase's requirement).
- **Create post** (§7.7, route `/community/create`): shipped here (D5) because the roadmap
  assigned it to neither 09-03 nor 09-04, and both feed CTAs ("+ Create New Post" and the
  empty state's "Create Post") target it.
- **Four backend repairs 9.3's own views depend on** (D1–D4): anonymous read on the
  community read surfaces, the deleted-post feed leak, the vote response's missing own-state
  flag, and community write throttling that currently cannot engage.

**What does NOT ship here:** post detail + 1-level comments (§7.8), analytics (§7.9),
notification center (§7.10), settings (§7.11), reporting UI (§7.12), PWA/service worker —
all 9.4 (D5 keeps §7.8 there; the feed's comment *count* comes from the card payload and
needs no comments client). Staff UI stays deferred (9.2 D2). `/community/categories/` stays
unbuilt by decision (D7).

<decisions>
## Decisions (alternatives and evidence in the discussion log)

| # | Decision | Choice |
|---|---|---|
| D1 | Community **read** access | **Open anonymous read**: `GET` on posts list/detail and comments list/detail becomes anonymous-allowed, because 05 §3.1 already routes `/community` publicly for all roles and 04 §6/§118 make public feed reading a configured option. Writes are untouched (auth required). Anonymous traffic is bounded by a read throttle with a scope declared **on the view** (7.2 R1); authenticated reads keep 5.2's documented unthrottled-browsing contract, so the throttle engages only for anonymous callers. |
| D2 | The deleted-post feed leak | Fixed in 9.3, not worked around: `feed_queryset` filters `is_deleted=False` (`trending_queryset` already does), and `test_deleted_posts_absent_from_feed` is repaired to assert **by id** in both the default feed and `?search=` — it currently asserts on the masked tombstone title, so it passed while the bug was live. |
| D3 | Vote response truthfulness | The vote mutation response gains `has_voted` — **one name**, shared with the feed card, so the optimistic pill reconciles against the server rather than its own optimism. 409 `already_voted` is treated as "you are already voted", not as a failure to roll back. |
| D4 | Community write throttling | Made real: `throttle_scope = CommunityWriteRateThrottle.scope` on every view that attaches the class, `throttle_classes` added to `PostListCreateView` (it declares none today), and a test that proves the bucket actually 429s plus an introspection test that every write view declares the scope. |
| D5 | §7.7 create post | **In 9.3.** The roadmap left `/community/create` unassigned between 09-03 and 09-04; it is the feed's write path and both feed CTAs target it, so shipping the feed without it would leave two dead ends. §7.8 post detail + comments stays 9.4. |
| D6 | Dashboard's stream-filtered discussions | **Approximated, recorded:** the block shows the community's newest posts. A genuine hiring-stream filter would need a new query parameter on the feed endpoint (posts carry a category; the stream lives on the author's profile), which the phase does not buy. Divergence recorded against §7.4's "in your stream". |
| D7 | Category vocabulary | The `GET /posts/categories/` endpoint stays **unbuilt** (declined this phase), so the 12 keys are held in one frontend constant module with a test pinning the exact set. This is a deliberate, recorded duplication of a settings-held vocabulary — the project's rule is "consume, never re-type" — and it is reclaimed the moment the endpoint ships. |
| D8 | Stitch usage | Mockups generated for all four 9.3 surfaces before implementation (7 screens: dashboard desktop+mobile, timeline, timeline modal, feed desktop+mobile, create post), from the same design system as 9.2. **Reconciled afterwards, not during:** Task 1's `grep -cE '^[0-9a-f]{32}$'` verification proved the IDs were recorded, not that the designs were used — see `09.3-DESIGN-RECONCILIATION.md`. |
</decisions>

## Resolved at plan time

1. **Feed read access** → D1 (anonymous read opened; the SPA's public route table and 05 §3.1 win over the shipped auth-required view).
2. **Optimistic-pill reconciliation** → D3 (the mutation response carries `has_voted`; the pill reconciles on success and rolls back on failure with a §6.7.1 error toast — the toast provider must be mounted, it currently is not).
3. **Scope of the "create post" gap** → D5 (in 9.3).
4. **Stepper source of truth** → the roadmap is built from `GET /timeline/` rows mapped onto the §7.4 milestone sequence (Interview → Selection → Offer → Survey → JL → Join); the dashboard payload's `latest_event` is a cross-check, not the source, because the stepper needs every milestone's date.

Remaining deliberate non-decisions: the §7.5 "Automatically update my current status" checkbox is
sent as the timeline event's own auto-sync (4.1's walk-the-chain does it server-side; the wizard
already proved that path) — no new flag is invented client-side.

<findings>
## Findings carried into this phase

1. **The feed requires auth while the SPA routes it publicly** — a visitor to `/community`
   currently gets a 401 from the API, so the route table and the backend disagree (D1).
2. **`test_deleted_posts_absent_from_feed` is vacuous** — it asserts the literal title is absent
   from a list of *masked* titles, which is true whether or not deleted posts leak (D2). Also
   verified live: `apps/community/views_services.feed_queryset` has no `is_deleted` filter.
3. **`PostListCreateView` declares no `throttle_classes`** (5.2 F2) and **none of the seven
   community write views declares `throttle_scope`**, so `CommunityWriteRateThrottle` allows every
   request (DRF's `ScopedRateThrottle` returns True when the view declares no scope) — 04 §41/§42's
   limits are decorative (D4).
4. **`VoteSerializer` returns no own-state flag**, so a client cannot read back the state it just
   changed (D3).
5. **`settings/base.py:169` claims "5.2's GET /posts/categories/ serves these same keys + labels"**
   and 04's endpoint inventory lists `GET /api/v1/posts/categories/`, but no view, route, or test
   for it exists anywhere in the tree (D7).
6. **`ToastProvider` is not mounted** — `App.tsx` composes ErrorBoundary → ThemeProvider →
   AuthProvider → RouterProvider; `useToast()` therefore throws on any page. §6.8's
   rollback-with-error-toast needs the provider added.
7. **The author payload's `avatar_seed` is the server's palette index** (5.2's HMAC over the
   candidate id) — the client maps the index to a colour; it must never recompute the hash.
</findings>
