## Web container bootstrap

| Option | Description | Selected |
|--------|-------------|----------|
| Placeholder server | Tiny Python stdlib HTTP responder on :8000 — proves ports/networks/volumes/healthchecks now; entrypoint swapped to gunicorn in 1.2 | ✓ |
| Defined-but-dormant | Declare the service with build context but `profiles: ["full"]` so it only starts when explicitly invoked; topology proves out partially | |
| Defer web to 1.2 | 1.1 composes only db/redis (+nginx); the 6-service clean boot gets verified at the start of 1.2 instead | |

| Option | Description | Selected |
|--------|-------------|----------|
| Yes — same treatment as web | Whatever web gets, celery gets: placeholder heartbeat task now, real tasks in 1.2; keeps the full 6-service boot in 1.1 | ✓ |

**User's choice:** Placeholder server; celery gets identical treatment (both recommended options)
**Notes:** User picked recommendations across the board; deterministic full-topology boot in 1.1 was the driving preference.

## Celery worker layout

| Option | Description | Selected |
|--------|-------------|----------|
| One worker, all queues | Single celery_worker consuming `-Q default,notifications,maintenance` — simplest, right for MVP scale; routing map in 1.2 config | ✓ |
| Worker per queue | Three separate services — isolation now, but 3× image pulls and more RAM for zero traffic | |

| Option | Description | Selected |
|--------|-------------|----------|
| Identical layout | Same single-worker/3-queue shape in both files; only env vars and resource limits differ | ✓ |
| Prod splits later | Single worker in dev; prod compose separates notifications worker for push latency isolation | |

**User's choice:** One worker with all queues; identical in dev and prod (both recommended options)
**Notes:** Can split later when a queue actually needs isolation.

## Version pinning strategy

| Option | Description | Selected |
|--------|-------------|----------|
| Exact minor pins | e.g. postgres:16.x-alpine, redis:7.x-alpine, python:3.11.x-slim (exact current tags verified at build time) — reproducible; dependabot can automate later | ✓ |
| Minor floats | postgres:16-alpine style — automatic CVE patch uptake, but rebuilds can shift behavior | |
| Digest pinning | @sha256 digests — maximum reproducibility, heaviest maintenance | |

| Option | Description | Selected |
|--------|-------------|----------|
| One shared Dockerfile | python:3.11-slim base, placeholder entrypoint — same image for web + celery_worker + celery_beat with different commands; 1.2 only swaps entrypoints | ✓ |
| Stock images + bind mounts | No Dockerfile yet — placeholders off python:3.11 with mounted scripts; Dockerfile in 1.2 | |
| Multi-stage builder now | Builder stage + slim runtime from day one — premature while app is a placeholder | |

**User's choice:** Exact minor pins; one shared Dockerfile (both recommended options)
**Notes:** No multi-stage complexity until the real Django app exists.

## Boot order & healthchecks

| Option | Description | Selected |
|--------|-------------|----------|
| Healthcheck-gated chain | db/redis get healthchecks (pg_isready, redis-cli ping); web/celery use depends_on: condition: service_healthy; nginx waits on web service_started. First `docker compose up` boots clean every time | ✓ |
| Minimal gating | Only web depends on db/redis health; celery/beat/nginx just use service_started — simpler files, occasional first-boot retries | |
| Maximum strictness | Everything gated with restart policies + aggressive start intervals — more config surface | |

**User's choice:** Healthcheck-gated chain (recommended option)
**Notes:** Deterministic first boot is the phase's core felt requirement.

## Volumes & env layout

| Option | Description | Selected |
|--------|-------------|----------|
| Named vols + dev bind mounts | Named volumes postgres_data + redis_data (per spec); source bind-mounted into web/celery in dev for hot-reload; single root .env via compose env_file in dev; prod env vars injected at deployment | ✓ |
| Bind mounts everywhere | Bind mounts only for everything including data dirs — risks permission issues on Windows hosts | |
| Named vols only | Everything named volumes, code baked into images even in dev — no hot-reload | |

**User's choice:** Named vols + dev bind mounts (recommended option)
**Notes:** Windows host machine made the bind-mounts-everywhere option unattractive.
