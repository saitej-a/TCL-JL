<research_summary>
## Summary

Verified current exact image tags for the three pinned base images (D-07): **PostgreSQL 16.15** (released 2026-08-13, per postgresql.org), **Redis OSS 7.4.11** (released 2026-08-17, per endoflife.date registry data — a CVE security release landed ~2026-09-18 in the 7.4 line, making 7.4.11 the safe pin), and **Python 3.11.12** (3.11.12-slim tag confirmed live on Docker Hub). Alpine variants follow the official images' per-release tag convention; the plan includes a build-time `docker manifest inspect` verification step with documented fallbacks.

Compose v2 long syntax (`depends_on: condition: service_healthy`) is the current documented approach for deterministic boot order (docs.docker.com/compose/how-tos/startup-order). Modern compose files **omit the top-level `version:` key** (obsolete in Compose v2 and warned against). Windows host specifics matter: CRLF line endings break nginx confs and shell entrypoints (fix with `.gitattributes eol=lf`), and placeholders must bind `0.0.0.0` (container-localhost is unreachable through the bridge network).

**Primary recommendation:** Compose v2 files without `version:`, exact pins `postgres:16.15-alpine`, `redis:7.4.11-alpine`, `python:3.11.12-slim`, healthcheck-gated chain, repo-wide `.gitattributes` forcing LF for `*.sh`, `*.conf`, `*.yml`, and placeholder scripts that bind `0.0.0.0`.
</research_summary>

<architecture_patterns>
## Architecture Patterns

### System Architecture Diagram

```
                   docker compose (dev)                      
   Host :80 ──► [nginx] ──proxy_pass──► [web :8000]          
                    │                          │ depends_on: service_healthy
                    │                    ┌─────┴─────┐          
                    │                    ▼           ▼          
                    │              [db pg:5432] [redis :6379]   
                    │                    ▲           ▲          
                    │                    └─────┬─────┘          
                    │                          │ depends_on: service_healthy
                    │              [celery_worker -Q 3 queues]   
                    │                          │               
                    │                  [celery_beat scheduler]   
                    ▼                                          
        named volumes: postgres_data, redis_data               
        dev only: source bind-mount → web + celery containers  
```

Data flow: every external request enters via nginx → web; web and celery both consume db/redis; beat enqueues to broker consumed by worker. First-boot order is enforced by healthchecks, not sleep timers.

### Recommended Project Structure
```
├── .env.example            # template for root .env (dev)
├── .gitattributes          # eol=lf for sh/conf/yml
├── .gitignore              # T1.1 exclusions + nginx/certs/
├── Makefile                # up, down, logs, ps, rebuild
├── docker-compose.yml      # dev (6 services)
├── docker-compose.prod.yml # prod (6 services, TLS)
├── Dockerfile              # shared: python:3.11.12-slim + placeholder entrypoint
├── docker/
│   └── entrypoint.sh       # placeholder responder / celery placeholder
└── nginx/
    ├── nginx.dev.conf      # HTTP :80 → web:8000
    ├── nginx.prod.conf     # TLS 1.3 listen + HSTS → web:8000
    └── certs/              # self-signed placeholders (gitignored)
```

### Pattern 1: Healthcheck-gated depends_on (Compose v2 long syntax)
**What:** Dependency services declare `healthcheck`; consumers gate on `condition: service_healthy`.
**When to use:** Any first-boot determinism requirement — this phase's core criterion.
**Example:**
```yaml
# Source: docs.docker.com/compose/how-tos/startup-order
services:
  db:
    image: postgres:16.15-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 15s   # first-boot initdb takes time
  web:
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy
```

### Pattern 2: One image, many roles via command override
**What:** Single Dockerfile; compose `command:` differentiates web/worker/beat.
**When to use:** Identical runtime deps across services (D-08) — no image divergence to maintain.
**Example:**
```yaml
  celery_worker:
    build: .
    command: ["python", "/app/docker/celery_placeholder.py"]
  celery_beat:
    build: .
    command: ["python", "/app/docker/beat_placeholder.py"]
```

### Anti-Patterns to Avoid
- **`version:` top-level key in compose files:** obsolete in Compose v2 — emits a warning; omit it.
- **Binding placeholders to 127.0.0.1:** unreachable from host/other containers on the bridge network — bind `0.0.0.0`.
- **Sleep-timer boot ordering (`sleep 10 &&`):** nondeterministic; healthchecks exist for this (D-09).
- **CRLF in mounted conf/scripts:** nginx fails with obscure errors on Windows checkouts; `.gitattributes` prevents.
- **Committing `.env` or `nginx/certs/*`:** violates T1.1 and leaks placeholders; gitignore both explicitly.
</architecture_patterns>

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| DB readiness probe | Custom Python socket check | `pg_isready` (in postgres image) | Handles auth/startup states natively |
| Redis readiness probe | TCP connect hack | `redis-cli ping` (in redis image) | Native, one-liner, zero deps |
| TLS cert generation for dev | Manual openssl ceremony in docs | One `openssl req -x509` command scripted in 1.1 | Reproducible placeholder certs; 10.2 replaces |
| Process supervision | supervisor/init in container | Compose `restart: unless-stopped` where needed | Compose owns lifecycle |
</dont_hand_roll>

<common_pitfalls>
### Pitfall 1: Postgres first-boot initdb races
**What goes wrong:** `pg_isready` fails during initial cluster creation; dependent services crash-loop.
**Why it happens:** initdb takes seconds-to-minutes on first run; default healthcheck intervals too tight.
**How to avoid:** `start_period: 15s`+ on db healthcheck; `retries: 10`.
**Warning signs:** `docker compose ps` shows db `starting` while web exits.

### Pitfall 2: Windows CRLF corrupts mounted configs
**What goes wrong:** nginx: `nginx: [emerg] unknown directive` on a perfectly valid conf.
**Why it happens:** Git checkout on Windows converts LF→CRLF; nginx parser rejects `\r`.
**How to avoid:** `.gitattributes` with `*.conf text eol=lf`, `*.sh text eol=lf`, `*.yml text eol=lf`; core.autocrlf=input for this repo.
**Warning signs:** confs parse locally but fail in container (or vice versa).

### Pitfall 3: `env_file` vs `environment` precedence surprises
**What goes wrong:** Prod secrets silently fall back to dev defaults (or vice versa).
**Why it happens:** `environment:` overrides `env_file:`; interpolation `${VAR}` resolves from shell/.env at parse time, not runtime.
**How to avoid:** Dev uses `env_file: .env` only; prod uses `environment:` explicit mapping; both validated by `docker compose config`.
**Warning signs:** Container sees `POSTGRES_PASSWORD` empty after `env_file` edit without `docker compose up -d --force-recreate`.
</common_pitfalls>
