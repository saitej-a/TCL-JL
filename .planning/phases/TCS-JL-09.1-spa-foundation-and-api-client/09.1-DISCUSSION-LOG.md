## 1. Token storage architecture

**Spec source:** 06 §3.3 gives two sanctioned deployment strategies — Option 1 (access token in memory,
refresh in `localStorage`, header Bearer) and Option 2 (both in `HttpOnly`, `Secure`, `SameSite=Strict`
cookies).

**Chosen:** Option 1 (D1), as recommended.

**Alternatives considered:**
- *Option 2 — HttpOnly cookies.* Genuinely stronger against XSS token theft, and the reason it was still
  worth asking: the spec lists it as an option, not a fallback. Rejected because it is not a frontend
  decision — it needs new cookie-issuing login/refresh endpoints in `apps/accounts`, CSRF middleware
  enforced on every state-changing route, and `SameSite=None` for the cross-origin deployment model. That
  is Phase 2's surface and would have made 9.1 a backend phase wearing a frontend hat.
- *Hybrid — access in memory, refresh in an HttpOnly cookie.* Not offered by the spec, would split the
  auth model across two mechanisms, and still needs the cookie endpoints. Rejected.

**Consequences recorded:** the access token's loss on reload (hence AuthContext's `booting` state, so the
guard does not bounce a reloading user), and the XSS surface on the refresh token (mitigated by 11
§9.6's `dangerouslySetInnerHTML` ban, React's default escaping, and the CSP Phase 10.2 validates).

## 2. Development serving topology

**Chosen:** host Vite on :5173 proxying `/api`, `/admin`, `/static`, `/media` → `http://localhost:80`
(D3), as recommended.

**Alternatives considered:**
- *Containerize a `frontend` service in compose.* Keeps "one command for the whole stack" (the Makefile's
  stated habit) and helps a teammate with no Node on the host. Rejected: a 7th service, a Dockerfile,
  a `node_modules` volume and a slower rebuild loop, for no functional gain — and the dev stack's
  documented shape is six services.
- *Direct cross-origin calls to `localhost:8000` with `CORS_ALLOWED_ORIGINS` added to `local.py`.* The
  smallest configuration change. Rejected because it makes development structurally different from
  production (two origins, a preflight on every request) and would hide exactly the class of mistake —
  wrong relative paths, missing proxy rules — that prod then exposes.

**Notable finding while deciding:** dev CORS is closed *on purpose* — `corsheaders` is installed and
`CORS_ALLOWED_ORIGINS` is populated only in `production.py`, so the SPA genuinely cannot call the API
cross-origin in dev without a settings change. The proxy route leaves that as-is.

## 3. Toolchain versions

**Chosen:** Tailwind v4 (CSS-first `@theme` via `@tailwindcss/vite`) + React 18 (D5/D6), as recommended.

**Alternatives considered:**
- *Tailwind v4 + React 19.* Same modern Tailwind, newer runtime. Rejected only because the roadmap and
  10_MVP_TASKS both say "React 18"; nothing in the spec needs a React 19 feature.
- *Tailwind v3 + React 18.* Would match 09 §13's tree literally, which lists `tailwind.config.js`.
  Rejected as the worse trade: v3's config-file style is the previous major, and carrying it forward for
  the sake of a directory listing trades a real technical default for a documentation detail. The
  deviation (no `tailwind.config.js`) is recorded in D5 so nobody "fixes" it later.

**Grounding:** a web check confirmed Tailwind v4 with the first-party Vite plugin is current practice in
2026 and that `@theme` replaces `tailwind.config.js` — this was worth verifying rather than assuming,
since the project has no JS tooling to infer from and the spec's tree predates v4.

## 4. Data layer between client and components

**Chosen:** spec-literal axios + per-domain hooks + Context (D7), as recommended.

**Alternatives considered:**
- *TanStack Query.* Free caching, retries and invalidation; would simplify 9.3's optimistic upvote
  rollback. Rejected because no spec mentions it, it is a second data-fetching paradigm alongside the
  Context the spec *does* name, and its cache semantics would have to be reconciled with the hand-rolled
  optimistic update the roadmap explicitly requires. Recorded as a deferred idea with the trigger
  condition (a view-level need for dedup/invalidation).

---

## 5. Frontend test tooling

**Chosen:** Vitest + React Testing Library now (D8), as recommended.

**Alternatives considered:**
- *Nothing until Phase 10's Playwright/Cypress E2E.* Keeps 9.1 lean, but the phase's central contract is
  concurrency behaviour (two concurrent 401s must produce **one** refresh), which E2E journeys are poor at
  proving and which would otherwise ship unverified.
- *Vitest now **and** wire it into CI in this phase.* Offered as a third option; not chosen. Recorded as an
  explicit deferral (D8) rather than an oversight, so the phase does not read as having "forgotten" CI.

**Design consequence:** the interceptor is tested by swapping the axios instance's `adapter` rather than
adding a mocking library — no new dependency for the one thing that most needs testing.

## 6. How far 9.1 goes beyond tokens + client (unanswered — default applied)

**Question skipped.** The recommended boundary is applied as D9 and flagged as open in
`09.1-CONTEXT.md`: 9.1 includes the react-router route table, `RequireAuth`, the Error Boundary and
placeholder page stubs, with the layout shells remaining 9.2's.

**Reasoning for the default:** without a bootable app the 401-replay contract can only be exercised in
tests, never in a browser — and this phase's acceptance criterion ("401 responses transparently refresh
and replay the original request") is far more convincing observed in a running app than asserted in
isolation. The counter-argument is real and is why it was asked: page stubs and a router are not in T9.1's
task line, and someone could reasonably want 9.1 to be a pure foundation with zero UI. Flipping this
before planning is a one-line scope edit; flipping it after is a plan rewrite, which is why it is recorded
as the phase's only open question.

## Findings surfaced during the discussion (not decisions)

1. **Refresh rotation is live with family reuse-detection.** `FamilyTokenRefreshSerializer` blacklists the
   submitted refresh token and revokes the *entire family* on replay. A naive interceptor would therefore
   log users out under concurrency. This single fact made the refresh queue (D2) the phase's core
   engineering content rather than a detail.
2. **Dev CORS is intentionally closed** (`CORS_ALLOWED_ORIGINS` only in `production.py`), which is what
   made the proxy topology a real decision rather than a preference.
3. **The built frontend is not served anywhere in production today.** `docker-compose.prod.yml` mounts
   only `nginx.prod.conf` and `./staticfiles` for nginx; 09 §10.1's documented
   `./frontend/dist:/var/www/frontend:ro` mount does not exist, and the root `vercel.json` builds the
   Django app. Recorded as D4 with its two 9.1-side obligations (env-driven base URL; a history-mode
   server fallback or deep links 404) and left open rather than guessed.
4. **`/api/v1/auth/` already covers every flow 9.2 needs** (register, verification verify/resend, login,
   rotating refresh, logout, password reset), and the client must send the refresh token to `logout/`,
   which independently justifies holding it. No backend change is required by this phase.
5. **The auth error codes the client must map** are `INVALID_CREDENTIALS`, `RATE_LIMITED` (with
   `Retry-After`) and `ACCOUNT_SUSPENDED` — and 401s from *unauthenticated* endpoints must bypass the
   refresh path, or a wrong-password login attempt would trigger a refresh and a logout.
