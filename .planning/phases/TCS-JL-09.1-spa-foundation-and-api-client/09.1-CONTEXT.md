- `src/types/` hand-written interfaces mirroring the backend contracts (11 §3.2 — no `any`, ever).

<decisions>
## Implementation Decisions

### Auth, tokens, and the refresh contract
- **D1: Header-based Bearer storage (06 §3.3 Option 1).** The access token lives **in memory only**
  (AuthContext; never `localStorage`, never a cookie). The refresh token lives in `localStorage` under a
  single namespaced key. Logout POSTs the refresh token to `/api/v1/auth/logout/` (which requires the
  access token and returns 204) and then clears both. A failed refresh clears the session and routes to
  `/login?next=<current>`. Consequences accepted: an XSS payload could read the refresh token, mitigated
  by 11 §9.6's blanket `dangerouslySetInnerHTML` prohibition, the strict CSP Phase 10.2 validates, and
  React's escaped-by-default rendering; and a full page reload loses the access token until the first
  silent refresh succeeds, which is why AuthContext exposes a `booting` state so guards do not bounce a
  reloading user to `/login` mid-refresh. Option 2 (HttpOnly cookies) was rejected: it needs new
  cookie-issuing endpoints, CSRF on every state-changing route and `SameSite=None` for cross-site use —
  backend work that belongs to Phase 2's surface, not to a frontend foundation phase.
- **D2: Single-flight refresh with a bounded replay — the phase's core contract.** Refresh token
  rotation is already live and **family reuse-detection is active**: `FamilyTokenRefreshSerializer`
  blacklists the submitted token at rotation and revokes *every* outstanding token in the family when a
  rotated token is replayed. A naive interceptor that lets two concurrent 401s each POST
  `/auth/token/refresh/` therefore logs the user out entirely. Shipped design: one module-level
  in-flight refresh promise; concurrent 401s await the same promise and then replay **once** with the new
  access token; each request carries a retry marker so a request can never be replayed twice (04 §112's
  "do not create infinite refresh loops"); the rotated refresh token is persisted immediately, before any
  queued replay fires; and a refresh that itself fails (expired, revoked, or family-revoked) clears the
  session rather than retrying. 401s that arrive **without** a Bearer token on the request (login,
  password reset, register) bypass the refresh path entirely — otherwise a wrong-password 401 would
  trigger a pointless refresh and a logout.
- **D3: Development topology — host Vite, proxied to nginx.** `npm run dev` runs on the host at :5173
  with Vite proxy rules for `/api`, `/admin`, `/static` and `/media` → `http://localhost:80` (the dev
  nginx service, which already fronts `web:8000` and serves `/static/`). The SPA is therefore
  same-origin with the API in dev and **no CORS change is needed** — `corsheaders` stays installed with
  `CORS_ALLOWED_ORIGINS` populated only in `production.py`, which is where a cross-origin deployment model
  belongs. The client reads its base URL from `VITE_API_BASE_URL` (default `/api/v1`), so dev stays
  relative while prod can point at the API origin. Rejected: containerizing a node service (a 7th compose
  service, Dockerfile and node_modules volume for no functional gain) and direct cross-origin calls to
  :8000 (two origins, a preflight on every request, and a dev/prod split that hides real proxy mistakes).
- **D4: The production serving model is deliberately left open, and 9.1 is built to be agnostic of it.**
  The frontend bundle is *not* wired into any prod topology today: `docker-compose.prod.yml` gives nginx
  only `nginx.prod.conf` + `./staticfiles:/var/www/static:ro` and a catch-all `proxy_pass` to `web:8000`
  (09 §10.1's documented `./frontend/dist:/var/www/frontend:ro` mount does **not** exist), while the
  root `vercel.json` builds the Django app. Whichever way 9.2–9.4 resolves it (nginx serving
  `frontend/dist`, or a Vercel CDN origin), two obligations are 9.1's and are recorded here: the base URL
  must come from the environment (D3), and **history-mode routing requires a server fallback** — a
  `try_files $uri /index.html` location on nginx, or a rewrite on Vercel — or a direct hit on any deep
  link (e.g. `/community/posts/:id`) 404s. Deferred rather than guessed.

### Design system and components
- **D5: Tailwind v4, CSS-first tokens.** Tailwind v4 via its first-party `@tailwindcss/vite` plugin, with
  the palette and semantic tokens declared in CSS `@theme` (no `tailwind.config.js` — the file 09 §13's
  tree lists is a v3 artifact) and dark mode defined as a class-strategy custom variant so 05 §4.2's
  `dark:` classes keep working. Tokens are declared in **two layers**: the raw scales (`brand-50…900`,
  the slate spectrum, and the emerald/amber/sky/rose semantic triples) exactly as 05 §4.1 gives them, and
  the semantic aliases (`background`, `surface`, `surface-elevated`, `primary`, `secondary`, `muted`,
  `border-default`, `input`) from 05 §4.2, so views can use either. The 05 §4.1.4 category badge matrix
  ships as a single typed map from category code → the three class strings per theme, because a second
  copy of those colors in a component is how a design system drifts.
- **D6: Pinned toolchain.** React 18 (the roadmap's wording; React 19 was declined), TypeScript with
  `strict: true` and no `any` anywhere (11 §3.2), Vite, and **npm** as the package manager — the repo has
  no JS tooling precedent, npm requires no extra tooling on the host or in CI, and adopting pnpm would
  add a second lockfile convention for no requirement that asks for it. ESLint ships with React Hooks
  rules (11 §3.2's matrix) and the lint/typecheck scripts are part of the phase gate, not optional.
- **D7: No client-side query library.** Server state is fetched through the typed domain modules plus
  per-domain hooks over `useState`/`useEffect`/`useReducer`, with Context for the two genuinely global
  concerns (session, theme) — spec-literal per 09 §13's tree, and no new dependency beyond `axios` and
  `react-router-dom`. 04 §114's cache candidates are *server-cached* reads (public stats, analytics,
  announcements), which need no client cache to be correct; if a view later proves to need request
  deduping or invalidation, that is a recorded follow-up, not a 9.1 guess.
- **D9: 9.1 includes a bootable app shell (default applied — the scope question went unanswered).**
  react-router with 05 §3.1's route table, `RequireAuth` redirecting unauthenticated visitors to
  `/login?next=<path>`, the route-level Error Boundary (11 §4.2), and placeholder page stubs so
  `npm run dev` renders a real app and the 401-replay path is exercisable in a browser rather than only in
  tests. The **layout shells stay 9.2's** (05 §5's visitor/desktop/tablet/mobile chrome, navigation and
  the tab bar) — 9.1 provides the router, the guard, the providers and stub pages that 9.2 fills in. If
  you would rather 9.1 stop at tokens + client + components with no routing, this is the one decision to
  flip before planning.
- **D10: The component library is T9.3's set plus two primitives.** `Button`, `Input`, `Textarea`
  (with character tally), `Badge` (matrix-bound), `Modal`, `Toast`, `Skeleton` — and, added here rather
  than invented in 9.2/9.4: `Disclaimer` (05 §5.6's text verbatim, so every later placement renders the
  same string) and `EmptyState` (11's Phase 9 directive that every list view has one). Component APIs are
  typed with explicit prop interfaces; no component reads a token from storage directly, and none uses
  `dangerouslySetInnerHTML` (11 §9.6).

### Tests
- **D8: Vitest + React Testing Library now; CI wiring deliberately deferred.** The 401 refresh-and-replay
  contract, the single-flight queue and the token store are logic and are tested headlessly with jsdom —
  the concurrency proof (two concurrent 401s producing **one** refresh call and two replays) is the test
  this phase most needs. The interceptor is exercised by swapping the axios instance's `adapter`, which
  needs no extra mocking dependency. `npm test` is part of this phase's gate. **CI is not touched**: the
  user chose to add the suite now and wire it into `.github/workflows/ci.yml` later, so today's CI still
  runs pytest + ruff only, and this is recorded as a deliberate deferral rather than an oversight.
</decisions>

## Existing Code Insights

### Reusable Assets
- **Nothing frontend exists yet** — no `package.json`, no `frontend/`, no node in any compose service.
  This phase creates the workspace from scratch; there is no prior convention to match, which is why the
  toolchain pins (D6) are recorded as decisions rather than inherited.
- `nginx/nginx.dev.conf` — already the single dev origin (`:80` → `web:8000`, serving `/static/` from
  `./staticfiles`), so the Vite proxy target in D3 needs no new infrastructure.
- `config/settings/local.py` — `ALLOWED_HOSTS = ["localhost", "127.0.0.1", "nginx", "web"]`; the proxy
  keeps the browser on `localhost`, so no settings change is required.
- `config/settings/production.py` — `CORS_ALLOWED_ORIGINS` and `CSRF_TRUSTED_ORIGINS` are already
  environment-driven, which is the hook a cross-origin production deployment would use.

### Established Patterns To Carry Over
- **One writer, no drift** (8.2's lesson): the component library is the single source of a visual
  decision — colors, radii and badge mappings live in tokens and one typed map, never re-typed per view.
- **Env-driven configuration, settings-read at call time** (backend precedent, e.g. throttle rates and
  `POST_CATEGORIES`): `import.meta.env` for the API base URL, read through one module so a change has one
  home.
- **Byte-exact external names** (the 7.2/8.2 route lesson): API paths, error codes and the disclaimer
  string are copied verbatim from the specs, with tests asserting the exact strings rather than substrings.
- **Every phase ships a gate**: lint + typecheck + tests + a live check. D8 gives 9.1 the same, minus the
  CI wiring the user deferred.

### Integration Points
- `frontend/` (new) at the repo root, per 09 §13.
- `nginx/nginx.prod.conf` + `docker-compose.prod.yml` — the SPA bundle is **not** mounted there today;
  whichever serving model wins needs the history-mode fallback (D4).
- `.github/workflows/ci.yml` — unchanged by this phase (D8); adding a frontend job is a recorded
  follow-up.
- The API itself is already complete for every view 9.2–9.4 will build: auth (2.2), profiles (3.2),
  timeline (4.2), community (5.2), notifications/preferences/devices (6.2), analytics (7.2) and
  moderation (8.2). 9.1 needs **no backend change**.

<specifics>
## Specific Ideas

- `src/api/client.ts` exports a configured axios instance plus a tiny typed surface: `apiGet<T>`,
  `apiPost<T>`, `apiPatch<T>`, `apiDelete`, and an `ApiError` class carrying `code`, `message`,
  `status` and `details` normalized from 04 §10 — so hooks never destructure DRF bodies by hand.
- Token storage is a single module (`src/api/tokenStore.ts`) with `get/set/clear` for the refresh token
  and an in-memory access token accessor. The interceptor and AuthContext both go through it; nothing else
  touches `localStorage`, which makes D1 auditable by grep.
- The refresh queue is deliberately not React state: it is a module-level promise, so two components
  firing concurrent 401s share one refresh even though they share no React tree.
- Router: `createBrowserRouter` (history mode, hence D4's fallback requirement) with route-level lazy
  loading left for 9.2–9.4 to introduce when the views are real; the guard is a wrapper component rather
  than a loader, so it can read AuthContext.
- `RequireAuth` must not bounce a reloading user: while AuthContext is `booting` (refresh in flight) the
  guard renders a skeleton, never a redirect.
- Skeleton loaders are the default for every pending state (05 §6.7.2) — the placeholder pages ship with
  them so 9.2–9.4 inherit the pattern rather than inventing spinners.
</specifics>
