    3. `frontend/src/api/client.ts` — the 04 §112 contract:
       - One axios instance with `baseURL: import.meta.env.VITE_API_BASE_URL ?? "/api/v1"` and

       - **Request interceptor**: attach `Authorization: Bearer <access>` when an access token exists;
         otherwise attach nothing (this is what makes auth-endpoint 401s bypass the refresh path).
       - **Response interceptor** implementing D2 exactly:
         * Non-401 errors → reject with the normalized `ApiError`.
         * 401 on a request that carried **no** Bearer token → reject as-is (login/register/reset).
         * 401 on a request that carried a token → `if (error.config._replayed) { clearSession();

         * Otherwise `await refreshOnce()`: a **module-level** `let refreshInFlight: Promise<string> |

           resolving; set the new access token in memory; mark the config `_replayed = true` and
           re-issue the original request through the same instance so the caller receives the real
           response.

           original request with a typed `SessionExpiredError` so AuthContext can route to
           `/login`. Reset `refreshInFlight` in a `finally` in every path.
       - Typed helpers `apiGet<T>`, `apiPost<T>`, `apiPatch<T>`, `apiDelete<T>` and a
         `Paginated<T>` type mirroring 04 §9 (`count`, `next`, `previous`, `results`) in
         `src/types/api.ts`.

<threat_model>
**T-09.1-01 (HIGH): Concurrent 401s revoke the token family.** Refresh rotation ships with family
reuse-detection, so two refreshes from one stored token blacklist every outstanding token and log the
user out — the exact failure a naive interceptor produces under normal concurrency (a page issuing two
authed requests when the access token has expired). Mitigation: the module-level single-flight promise
plus the `_replayed` marker (D2), with a call-count assertion in the tests. Verified by: the concurrent
401 test asserting exactly one refresh POST and two replays.
**T-09.1-02 (HIGH): Refresh token theft via XSS.** The refresh token is readable JavaScript by design
(06 §3.3 Option 1). Mitigation: `dangerouslySetInnerHTML` is banned project-wide (11 §9.6), React escapes
by default, the access token never persists, logout blacklists the refresh token, and the CSP Phase 10.2
validates is the enforcement of last resort. Verified by: a lint rule/test-style guard (no
`dangerouslySetInnerHTML` in `src/**`) plus the storage test asserting the access token is never written
to `localStorage`/`sessionStorage`.
**T-09.1-03 (MEDIUM): A looping interceptor hammers the auth endpoints and locks accounts out
(429 → 5/min login, and refresh reuse detection).** Mitigation: the `_replayed` marker makes a second
replay impossible, refresh failure clears the session instead of retrying, and no retry/backoff loop
wraps the refresh call. Verified by: the "401 after replay does not refresh again" and "refresh failure
clears the session" tests.
**T-09.1-04 (MEDIUM): A reloading user is treated as signed out.** A guard that redirects while the
silent refresh is in flight bounces legitimate users to `/login` and, if they re-authenticate, can
create a second token family. Mitigation: the explicit `booting` state with a skeleton (D1/D9).
Verified by: the RequireAuth booting test.
**T-09.1-05 (MEDIUM): Different origins in dev hide production breakage.** A dev-only CORS allowance or
an absolute API URL would let a broken relative-path/proxy setup pass review, then 404 in production.
Mitigation: the D3 proxy keeps the SPA same-origin in dev exactly as a reverse proxy will in production,
and the base URL is read in one module behind `VITE_API_BASE_URL`. Verified by: the proxy proof (200
