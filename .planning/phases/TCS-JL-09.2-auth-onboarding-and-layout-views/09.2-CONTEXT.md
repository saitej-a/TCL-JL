## Phase Boundary

Phase 9.2 turns 9.1's bootable stub shell into the real application chrome and the
pre-dashboard user journey:

- **Responsive layout shells** (UI-01): desktop 3-column (§5.2: sidebar 240px + center +
  right rail 320px), tablet 2-column (§5.3), mobile top-bar + bottom tab bar (§5.4, 5 tabs,
  ≥44px touch targets). The §5.5 announcement banner sits above the shell in all breakpoints.
- **Landing page** (§7.1) with live stats fed from `GET /api/v1/public/stats/` (verified
  working through the dev proxy in 9.1).
- **Six auth screens** (§7.2.1–7.2.6): login, register, verify-email status, resend
  verification, forgot password, reset password.
- **3-step onboarding wizard** (§7.3): offer details → current status → review/finish.
- **One explicit backend task** (D1): replace the `profile_completed` hardcoded-`False` stub
  with real profile-completion logic so the onboarding gate is truthful.

**What does NOT ship here:** dashboard/timeline/feed content (9.3), post detail/analytics/
notifications/PWA (9.4), staff moderation UI (deferred entirely — D2).

## Backend contracts confirmed for this phase

- `POST /api/v1/auth/register/` → creates account; email verification flow follows.
- `POST /api/v1/auth/login/` → `{access, refresh, user}`; `user.is_verified` drives the
  unverified banner on every auth-gated screen.
- `GET /api/v1/auth/me/` (UserPrivateSerializer) → `profile_completed` flag gates the
  wizard redirect. **This flag is currently hardcoded `False`** — D1 makes fixing it a
  9.2 task, not a plan-time surprise.
- `POST /api/v1/profile/` accepts every wizard step-1 field **plus** the `current_status`
  side-channel (the one status field not expressed as a timeline event).
- `POST /api/v1/timeline/` events (`INTERVIEW`, `SELECTION`, `OFFER_LETTER`,
  `READINESS_SURVEY`) auto-sync candidate status via 4.1's walk-the-chain — step 2 of the
  wizard writes through this path.
- `GET /api/v1/community/announcements/` feeds the §5.5 banner (9.1 proof used it live).

<open_questions>
## Open for planning

1. **Onboarding gating UX** — §7.3 says the wizard follows login when
   `profile_completed` is false. Confirm the exact mechanism at plan time: RequireAuth
   checks the flag and redirects, vs. dashboard renders a blocking wizard card. (Redirect
   matches the spec's "3-step onboarding" framing; blocking card is gentler. Small, but
   it shapes the route table.)
2. **Banner dismiss persistence** — §5.5 specifies dismissal; decide localStorage key
   semantics (per-announcement ID vs. global) during planning; trivial either way.
3. **Wizard write order** — step 1 `POST /profile/` then step 2 timeline event(s), vs.
   batched at finish. Backend accepts both shapes; plan should pick one and test it.
</open_questions>

<findings>
## Findings carried into this phase

1. **`profile_completed` is hardcoded `False`** in the shipped `UserPrivateSerializer`
   (9.1 execution finding, now promoted to D1's backend task).
2. **`AuthorPublicSerializer` ships no `avatar_seed`** — IdentityPill derives the pastel
   from `display_name` (9.1 decision, unchanged; landing/shell mockups assume it).
3. **O1 `/admin` collision** (9.1 verification finding): staff routes collide with the
   Django admin proxy reservation in dev. Moot for 9.2 while staff nav is deferred (D2);
   must be resolved before any staff UI phase.
4. **`is_verified` rides the login response** — the unverified-account banner on auth
   screens needs no extra endpoint call.
</findings>
