## 1. The onboarding gate: `profile_completed` is a hardcoded stub

**The situation:** the wizard's gate flag in `UserPrivateSerializer` is hardcoded `False`
(a 9.1 execution finding). Every signed-in user would be redirected to onboarding forever,
and skipping it stores nothing. The frontend could hide this — treat the flag as advisory,
don't redirect, let users "complete" onboarding client-side — but that ships a lie at the
heart of the phase's central flow.

**Chosen:** fix the backend stub as an **explicit 9.2 task** (D1).

**Alternatives considered:**
- *Frontend-only workaround.* No backend change lands in the frontend phase, and the flag
  is only a serializer field away from correct. But it means the product's real gate is
  fiction, and every later phase builds on the fiction. Rejected.
- *Defer to a dedicated backend phase.* Onboarding is 9.2's deliverable; shipping it
  knowingly gated on a false flag contradicts the phase's own done-when. Rejected.

**Scope of the fix (for planning):** compute `profile_completed` from real state — profile
row exists with required fields (hiring_type/role/region/batch/offer date) — with serializer
tests. Small, testable, backend-side.

## 2. Staff navigation in this phase?

**The situation:** 05 §3.1 includes staff routes, and the sidebar mockups show admin-ish
nav real estate. But the `is_staff` display field doesn't exist on the user serializer
(9.1 finding), and O1 (9.1 verification) means staff SPA routes are unreachable at their
spec'd paths in dev until the `/admin` proxy collision is decided.

**Chosen:** defer staff navigation entirely (D2) — no staff links, no staff route
protected-navigation, no `is_staff` display in 9.2.

**Alternatives considered:**
- *Include staff nav links now.* They'd point at routes that 404 in dev (O1) and at
  dashboards that don't exist until a staff phase. Dead UI is worse than absent UI. Rejected.
- *Decide O1 in this phase so staff routes work.* O1 is a topology decision (relocate UI
  staff pages vs. split proxy vs. spec change) that deserves its own discussion with the
  staff-UI phase in front of it. Bundling it here would make 9.2 carry an unresolved
  architecture question. Rejected — moved with D2 to the staff phase.

## 3. The §5.5 announcement banner

**The situation:** §5.5 specifies a dismissible banner above the shell, and the backend
announcements endpoint is live (proven through the dev proxy in 9.1).

**Chosen:** include it in 9.2 (D3) — banner component fed by
`GET /api/v1/community/announcements/`, with dismiss persistence.

**Alternatives considered:**
- *Defer to the dashboard phase (9.3).* The banner is shell chrome, not dashboard content;
  the roadmap's done-when ("layout adapts across breakpoints with the disclaimer present")
  is about the shell, and the banner is part of the shell. Rejected.
- *Hardcode a demo banner.* Zero backend wiring, but the endpoint is live and the spec
  says the banner shows real announcements. Rejected.

**Left to planning:** the dismiss-persistence key semantics (per-announcement ID vs.
global flag) — trivial either way, noted in the context record.

## 4. Stitch design generation scope

**The situation:** the standing directive makes Stitch the UI-design tool. The question
was how far to push generation before planning: full screen set, or just the ambiguous
ones (shells) and let execution fill in the card-pattern screens.

**Chosen:** full screen set for the phase's views (D4). Ten mockups were generated in the
`TCS Joining Tracker` Stitch project from the 05 §4-derived design system: desktop shell
(light + dark variant), mobile shell, landing, login, registration, forgot-password, and
onboarding steps 1–3. Screen IDs are catalogued in `09.2-CONTEXT.md`.

**Alternatives considered:**
- *Shells only.* Faster, but the auth card pattern and wizard step anatomy are exactly
  where consistency drifts; generating them now means planning sees one visual language.
- *Also generate the 3 remaining auth variants (verify-email, resend, reset) and the
  tablet breakpoint.* Deliberately not done: they are mechanical variants of the
  established patterns (same card geometry, error/success strips), and generating them
  during planning/execution if wanted is one tool call. Recorded as an honest coverage
  note in the context record rather than padded scope.

**Standing boundary:** Stitch output is design reference, not code — implementation stays
in `frontend/` against the 9.1 token layer with the spec's class strings.
