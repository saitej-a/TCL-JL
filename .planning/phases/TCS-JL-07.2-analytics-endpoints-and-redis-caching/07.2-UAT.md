## Tests

### 1. The five anonymous endpoints answer over HTTP
expected: The dev stack is up and the `analytics:*` cache namespace purged first (a stale payload persists up to 2h by design, D-05). All five reads — `/api/v1/analytics/overview/`, `/batches/`, `/hiring-types/`, `/regions/` and `/api/v1/public/stats/` — return HTTP 200 with no login or token, each carrying `data_source: "COMMUNITY_REPORTED"` and the community-data disclaimer.
result: pass

### 2. Per-row <5 suppression holds at the payload level
expected: Reading `/api/v1/analytics/batches/` (and the other breakdowns), every published row reports a sample of 5 or more — no row shows a count below 5, nothing is zeroed or labeled, and rows that would be below the floor are absent entirely. `/api/v1/public/stats/` never exposes counts below the floor. The drill asserts this over HTTP and it should match what the endpoints return.
result: pass

### 3. Both wait-time baselines are published side by side
expected: `/api/v1/analytics/overview/` contains two distinct wait-time metrics, each naming its baseline and disclosing its own sample: offer→JL (the 7.1 chain, `average_days` around 53.0 in the drill's seed) and READINESS_SURVEY→JL (survey baseline, `average_days` around 32.7). The two numbers are clearly different and each sample size is disclosed per source, so a reader can see they are not the same population.
result: pass

### 4. A typo'd filter gets a 400 that names the parameter
expected: `GET /api/v1/analytics/batches/?hiring_type=not-a-type`, `GET /api/v1/analytics/hiring-types/?batch=99999` and `GET /api/v1/analytics/regions/?hiring_type=bogus` each return HTTP 400 with `error: "invalid_filter"` and a `param` field naming the offending query-string parameter — never a silent 200 with community-wide numbers. `/api/v1/analytics/regions/` still answers 200 when the (deliberately unaccepted) `region` param is passed, since it consumes only `batch`/`hiring_type`.
result: pass
