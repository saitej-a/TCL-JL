# Phase 7.2: Analytics Endpoints & Redis Caching - Context

**Gathered:** 2026-09-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Roadmap plan **07-02** (MVP tasks T7.3–T7.10, requirements ANAL-01, ANAL-02, ANAL-05): put
7.1's read-only analytics service behind HTTP and make it cheap to serve.

**In scope**

1. **Four analytics endpoints** — `GET /api/v1/analytics/overview/` (04 §48),
   `/batches/` (§49), `/hiring-types/` (§50), `/regions/` (§51), all anonymous,
   all labeled `COMMUNITY_REPORTED`, all carrying the non-affiliation disclaimer.
2. **The public landing stats endpoint** — `GET /api/v1/public/stats/` (04 §80, T7.9),
   which 05_UI_UX §746 animates the landing-page counters from.
3. **Redis caching** — response payloads cached through Django's cache framework with a
   settings-held TTL, plus the `warm_analytics_cache` Celery task behind the beat entry
   `config/celery.py` has already reserved.
4. **Per-row suppression** — 7.1's `<5` floor applied to each result row (D-01), which
   *changes* the payloads 7.1 ships and requires updating its tests deliberately.
5. **A fifth wait-time metric** — survey→JL published alongside D1's offer→JL (D-13),
   surfaced through the overview payload (D-14).
6. **Read throttling and filter validation** — an anonymous `analytics_reads` scope (D-11)
   and whitelist validation of `?hiring_type=` / `?region=` / `?batch=` (D-12).

**Out of scope (explicit)**

- **`04 §52 /analytics/timeline/`** — deferred to backlog (D-10): no ANAL requirement owns it,
  §108's required-test list omits it, and it needs an event-level aggregation 7.1 did not build.
- **Any model or migration.** 7.1 shipped zero models and this phase adds none; the phase is
  read-only over `CandidateProfile` and `TimelineEvent`.
- **Per-candidate or per-event data of any kind** (§52's own rule), and any filter combination
  that could identify one candidate (§51).
- **OpenAPI/schema generation** (§109) — Phase 10.2; see Deferred Ideas.
- **Frontend consumption** — the landing page, dashboard and analytics screens are Phase 9
  (9.2/9.3/9.5). 7.2 ships the contract they read.

<decisions>
## Implementation Decisions

### Suppression granularity

- **D-01 — The `<5` floor applies to each result row, and a row below it is dropped entirely.**
  7.1 gated only the slice total, so a 200-candidate national slice could emit a batch row
  reporting 3 candidates — the differential-inference vector 4.2's residual-risk note named.
  Rows below the floor never appear: not zeroed, not labeled, not counted. — **Reversibility:**
  costly — this changes the published payload contract of all four analytics endpoints and
  requires updating tests that currently assert slice-level-only behaviour; undoing it after
  9.2–9.5 consume the contract re-opens an inference vector. Rejected: "floor each row and
  report how many groups were withheld" (the withheld count is itself a disclosure, and it
  tells a reader exactly where the small cohorts are).
- **D-02 — If no row clears the floor, the response is the standard suppression payload.**
  The 04 §53 shape (`data_source`, `suppressed: true`, message, disclaimer) — the same payload
  a below-floor *slice* returns. Never `suppressed: false` with an empty `results[]`, which
  would conflate "no data exists" with "data exists but is too small to show", and never the
  slice totals with the small rows quietly omitted (that reveals the omitted rows' aggregate by
  subtraction).
- **D-03 — One setting governs both levels.** `ANALYTICS_MIN_COHORT_SIZE` (default 5, unchanged
  from 4.2/7.1) is read at call time by both the slice gate and the per-row gate. A second
  `ANALYTICS_MIN_GROUP_SIZE` was rejected: two knobs that must stay in a privacy-ordering
  relationship are a misconfiguration waiting to happen, and no requirement asks for them to
  differ.

### Cache shape & warmup

- **D-04 — The cached unit is the assembled response payload, keyed per endpoint + filter
  signature.** 7.1's functions are reused verbatim, so there is exactly one code path that
  computes a metric and exactly one that serializes it. The overview payload ignores filters and
  is one key; the three breakdowns get a key per filter combination, written on first read and
  refreshed by the warmup for the unfiltered defaults. Rejected: caching a per-bucket aggregate
  snapshot and assembling at read time — it avoids combinatorial keys but needs a second
  assembly path beside 7.1's, which is the exact drift risk this project keeps finding.
- **D-05 — TTL is 7200s (two hours), held in a settings key read at call time.** The hourly
  warmup refreshes the hot keys; the TTL is the backstop, so a missed or failed beat run leaves
  data an hour stale rather than emptying the cache and stampeding live aggregations. **This is a
  recorded deviation from `10_MVP_TASKS.md` T7.8's `ttl = 15m`**, which cannot coexist with an
  hourly warmup — a 15-minute TTL expires three times per warmup cycle, making the beat task
  decorative. ROADMAP Phase 7 success criterion 4 (cached in Redis *with hourly warmup*) is the
  authoritative statement.
- **D-06 — `generated_at` is written into the cached payload at compute time.** A cache hit
  therefore reports when its numbers were computed, not when it was served. 04 §48 pins the key
  and 7.1's payloads omit it; computing it at response time would let a 59-minute-old payload
  claim to be current — the "silently stale" failure mode this project has already hit twice.
- **D-07 — `analytics.tasks.warm_analytics_cache` is routed to the `maintenance` queue.**
  `config/celery.py` already reserves the beat entry (`warm-analytics-cache-hourly`, `:45`) but
  `CELERY_TASK_ROUTES` has no entry for it, so today it would silently land on `default` and
  compete with request-driven email and push work. `maintenance` already carries
  `notifications.tasks.prune_stale_devices` — periodic refresh of derived data nobody is waiting
  on is exactly that queue's job. The decorator's `name=` must match the reserved path exactly,
  or the route silently does not apply (the 6.2 lesson).

### Endpoint surface & public exposure

- **D-08 — All five read endpoints are anonymous.** 04 §6 lists "Landing-page information" and
  "Public aggregate statistics" under Anonymous, so `AllowAny` is spec-mandated rather than
  chosen — no authentication class, no owner scoping (there is no owner; the data is aggregate).
- **D-09 — 7.2 builds 04 §80's `GET /api/v1/public/stats/`.** The roadmap's 07-02 names a
  "public landing stats endpoint" and T7.9 depends on T7.8, so it belongs to this phase, not to
  the 9.5 landing page. It is its own thin endpoint with its own cache key, returning §80's keys
  (`registered_candidates`, `community_posts`, `timeline_events`) — counts across three apps, so
  serving §48's overview payload from this URL was rejected as a shape deviation that would also
  make analytics reach into accounts/community/timeline tables.
- **D-10 — 04 §52 `/analytics/timeline/` is deferred to backlog, recorded as a known gap.**
  No ANAL requirement claims it, T7.3–T7.9 do not include it, §108's required tests omit it, and
  it needs an event-level aggregation over `TimelineEvent` that 7.1 deliberately did not build —
  plus a suppression rule for per-day counts, which is the most identifying shape in the spec.
  Recorded in Deferred Ideas with that reasoning so it is an acknowledged gap, not an oversight.
- **D-11 — An anonymous `analytics_reads` scope throttles these reads.** Cache keys multiply per
  filter combination, so an anonymous caller can walk region × hiring_type × batch and force
  uncached computation of the app's most expensive aggregate queries on every request. A scoped
  throttle is the existing project pattern (`apps/community/throttles.py`,
  `apps/accounts/throttles.py`); the exact rate is Claude's discretion (nominal 120/min, tuned
  for real users who will make single-digit calls per session). This deliberately departs from
  community's "read routes stay unthrottled" precedent, where reads are paginated and
  query-budgeted rather than aggregate scans.
- **D-12 — Filters are whitelist-validated; unknown values return 400.** `?hiring_type=` and
  `?region=` against the profile model's own choices, `?batch=` against settings' `BATCH_YEARS`
  (the established settings-held-tunable pattern). This bounds the cache key space — unbounded
  keys let an anonymous caller mint cache entries with junk — and turns a typo into a clear 400
  instead of a confidently wrong community-wide number. Rejected: silently ignoring unknown
  values (returns wrong data that looks right on a public stats page) and accepting any string
  (unbounded memory growth driven by anonymous input).

### ANAL-03's baseline & wait-time exposure

- **D-13 — Both intervals are published as separate metrics.** ANAL-03 reads "between **survey
  submission** and joining letter issuance" and T7.7 says `READINESS_SURVEY` → `JOINING_LETTER`;
  `READINESS_SURVEY` is a real `TimelineEvent` type and a real profile status, and the readiness
  survey is *later* than the offer, so the two intervals are materially different numbers and not
  interchangeable. So 7.2 publishes the requirement-literal survey→JL metric **and** D1's shipped
  offer→JL metric as two metrics, each with its own sample size and its own `<5` floor — closing
  ANAL-03 literally without discarding the wider sample that OFFER_LETTER's four-step fallback
  chain produces (per `12_SEED_DATA`, only ≈20% of the seeded cohort has a survey event, so a
  survey-only metric would frequently fall below the floor and suppress). — **Reversibility:**
  costly — the payload contract and REQUIREMENTS' ANAL-03 annotation both change; undoing it
  means publishing a number the spec does not ask for as the only number.
- **D-14 — Wait-time metrics surface through `/analytics/overview/`'s payload.** 04 §47–§53 define
  no wait-time endpoint, and waiting is exactly the "overview" quantity. 4.2's dashboard already
  serves threshold-suppressed community benchmarks, so it reads the cached overview payload
  rather than a second source. Rejected: a new `/analytics/wait-times/` endpoint (an invented API
  surface no spec section defines) and leaving the metric service-only (7.1 already computes it;
  ANAL-03 asks the system to *report* it).
- **D-15 — Deleted/anonymized accounts stay counted, exactly as 7.1's aggregations do today.**
  4.2's F1/F2 residual risk (deleting an account anonymizes it but keeps its profile row) is
  therefore *accepted* rather than fixed here. Rationale: 7.2 is a read-only phase and excluding
  tombstones would silently change the meaning of every cohort count relative to 4.2's dashboard
  — a behavior change dressed as a privacy fix, in a phase whose job is exposure, not retention.
  The consequence is recorded plainly in STATE.md: every public number includes candidates who
  have left the community, and the fix belongs with the retention model, not the endpoint.
  — **Reversibility:** costly — undoing it later changes published numbers retroactively, since
  "total tracked" would drop the moment the rule flips.
- **D-16 — Each metric discloses its baseline and its per-source sample sizes.** With two metrics
  published side by side, a reader must be able to see that they are not the same interval; and
  within the offer→JL metric, which of D1's four chain steps (offer event, interview event,
  profile offer date, profile interview date) resolved each sample, since a fallback-heavy sample
  is weaker evidence than an event-based one. Rejected: naming only the dominant baseline (still
  hides a mixed average) and publishing the aggregate alone with a sample size (two different
  intervals presented as one number — precisely the ambiguity D-13 exists to end).

### Claude's Discretion

Recorded so the planner does not re-ask; the user delegated these:

- **The `analytics_reads` rate** — declared as a `ScopedRateThrottle` subclass in a new
  `apps/analytics/throttles.py`, rate in `REST_FRAMEWORK["DEFAULT_THROTTLE_RATES"]` (nominal
  `120/min`). **Whether `/public/stats/` shares that scope** is left to the planner — it takes no
  filters so it needs one cache key, but it is the highest-volume anonymous endpoint in the app
  (every landing-page visit) and the first thing a scraper or a shared-NAT office would hit.
- **Cache key composition and namespacing** — a versioned prefix (so a payload-shape change can
  invalidate cleanly), with the filter signature in a stable order.
- **What the warmup refreshes** — the roadmap requires overview + batch; warming the unfiltered
  default of every cached endpoint is at least as cheap and leaves no cold default.
- **File layout** — `apps/analytics/views.py`, `urls.py`, `tasks.py`, `throttles.py` (plus a
  cache helper module if that keeps views thin). The project pattern is thin views over a service
  layer, and per-app `urls.py` included from `config/urls.py` under the shared `/api/v1/` prefix.
- **Test module naming** — §108 names seven required tests (`test_overview_analytics`,
  `test_batch_analytics`, `test_hiring_type_analytics`, `test_region_analytics`,
  `test_minimum_group_suppression`, `test_private_fields_not_in_analytics`,
  `test_analytics_marked_community_reported`); map them onto files under
  `apps/analytics/tests/` and honour T7.10's privacy/performance intent with the project's
  query-budget-as-tests convention.
- **Pagination does not apply** — these are single aggregate payloads, not lists; §49/§50's
  `results` array is a fixed-size bucket list, and `PAGE_SIZE = 20` governs paginated endpoints
  only.
- **Updating `apps/analytics/tests/test_phase_boundary.py`** — it currently *asserts* that
  `apps/analytics` has no `views.py`/`urls.py` and no `tasks.py`/cache import (7.1's D5 boundary).
  7.2 must rewrite those assertions deliberately into their inverse (the boundary has moved, and
  the app now has both) rather than delete the file.

</decisions>

### Established Patterns

- **Thin views over a service layer**; views translate domain errors into HTTP codes.
- **Foreign objects 404, never 403** — not applicable here (no object-level resources), which is
  itself worth one boundary test so a future filter cannot accidentally leak a foreign cohort.
- **Settings-held tunables read at call time** (`BATCH_YEARS`, `TRENDING_WINDOW_DAYS`,
  `ANALYTICS_MIN_COHORT_SIZE`) — D-05's TTL and D-11's rate join them.
- **Django's cache framework, never a raw redis client** (6.2 D3) — keeps the suite on
  `LocMemCache` and needs no Redis to run.
- **Celery task names are reserved centrally** in `CELERY_TASK_ROUTES`; a decorator `name=` that
  disagrees with the route silently goes to `default` (6.2's recorded lesson) — D-07.
- **`COMMUNITY_REPORTED` + disclaimer on every payload, suppressed or not** — 7.1's D4, asserted
  even for a zero-candidate cohort; ANAL-05's labeling half is already structural and 7.2 must
  keep it that way through the cache (a cached payload must not lose the labels).
- **Per-app `urls.py` included from `config/urls.py`** under the shared `/api/v1/` prefix.

<specifics>
## Specific Ideas

- 04 §48's `generated_at` example is `"2026-09-19T12:00:00Z"` — UTC, ISO-8601, `Z`-suffixed, not
  a local timestamp.
- 04 §53's suppression payload is the fixed contract and 7.1 already emits exactly it
  (`data_source`, `suppressed: true`, message, disclaimer) — D-02 reuses it rather than inventing
  a second "nothing to show" shape.
- 04 §80's landing payload is deliberately *not* analytics-shaped: `registered_candidates`,
  `community_posts`, `timeline_events` — three cross-app counts, not recruitment cohorts (D-09).
- The disclaimer sentence is spec text, not a paraphrase: "These figures are based on
  community-submitted data and are not official TCS statistics."
- 7.1's drill (`drill_07_01.py`) is the model for proving this phase live: seed into the real dev
  database, assert through the HTTP surface including a cache hit/warm, and restore the exact
  baseline counts (21/21 candidates, 66/66 events at last run).
