## Suppression granularity

### Where the `<5` floor applies

| Option | Description | Selected |
|--------|-------------|----------|
| Floor each row; suppress whole response if none survive | Per-row floor, whole-response suppression when nothing clears it | ✓ |
| Floor each row, and report how many groups were withheld | Also disclose the withheld-group count | |
| Keep the slice-total floor only, as 7.1 ships | No change to 7.1's payloads | |

**User's choice:** Floor each row; suppress the whole response if none survive
**Notes:** Resolves the residual-risk note 4.2 left on the differential-inference vector (a batch
row inside a large national slice could report 3). Context supplied beforehand: in the dev
dataset batch `2024` holds 3 candidates, so under a per-row floor that entire batch row
disappears from `/batches/` — the user was shown that consequence and chose it.

### When the slice clears the floor but every row inside it does not

| Option | Description | Selected |
|--------|-------------|----------|
| Return the standard suppression payload | The 04 §53 shape | ✓ |
| Return `suppressed: false` with an empty `results[]` | Distinguishes "no data" from "too small to show" | |
| Return the slice-total response and omit only the small rows | Keeps the totals | |

**User's choice:** Return the standard suppression payload (04 §53 shape)
**Notes:** Keeps one "nothing to show" payload for both cases rather than inventing a second
shape, and avoids revealing omitted rows' aggregate by subtraction.

### Which setting governs the two levels

| Option | Description | Selected |
|--------|-------------|----------|
| One `ANALYTICS_MIN_COHORT_SIZE` for both | Single knob for slice and row floors | ✓ |
| A second `ANALYTICS_MIN_GROUP_SIZE`, defaulting to the same 5 | Two independent knobs | |

**User's choice:** One `ANALYTICS_MIN_COHORT_SIZE` governs both levels
**Notes:** Two knobs that must maintain a privacy ordering are a misconfiguration risk, and
nothing in the requirements asks them to differ.

## Cache shape & warmup

### What gets cached

| Option | Description | Selected |
|--------|-------------|----------|
| Cache assembled payloads per endpoint+filter | Reuses 7.1's functions verbatim; overview is one key, breakdowns one per filter combination | ✓ |
| Cache the per-bucket aggregate snapshot, assemble at read time | Fewer keys, but needs a second assembly path beside 7.1's | |
| Cache only overview + batch | Exactly what ROADMAP criterion 4 names; streams and regions stay live | |

**User's choice:** Cache assembled payloads per endpoint + filter signature
**Notes:** Presented with the query-cost context — each 7.1 aggregation costs 1 + N queries (one
per bucket), and the Django-cache-not-raw-redis constraint from 6.2 D3 so the suite keeps running
on `LocMemCache`.

### TTL

| Option | Description | Selected |
|--------|-------------|----------|
| Two hours, as a backstop behind the warmup | A missed beat run leaves data stale, not the cache empty | ✓ |
| One hour, matching the warmup | Expiry tied exactly to the warmup cadence | |

**User's choice:** Two hours (7200s)
**Notes:** Recorded in CONTEXT as a deliberate deviation from `10_MVP_TASKS.md` T7.8's
`ttl = 15m`, which cannot coexist with an hourly warmup. ROADMAP Phase 7 criterion 4 is treated
as authoritative.

### `generated_at` semantics

| Option | Description | Selected |
|--------|-------------|----------|
| `generated_at` written into the cached payload | Reports when the numbers were computed | ✓ |
| `generated_at` computed at response time | Always reads as "now" | |
| Both: `generated_at` plus a served marker | Also exposes when the response was served | |

**User's choice:** Written into the cached payload at compute time
**Notes:** 04 §48 pins the key and 7.1's payloads omit it entirely — adding it is part of this
phase. Response-time computation was rejected as the "silently stale" failure mode this project
has already hit twice.

### Warmup queue

| Option | Description | Selected |
|--------|-------------|----------|
| Add a route to the `maintenance` queue | Joins `prune_stale_devices` on housekeeping | ✓ |
| Leave it unrouted on `default` | No settings change; competes with request-driven work | |
| Introduce a dedicated `analytics` queue | Cleanest isolation, needs a fourth queue and worker | |

**User's choice:** Route to `maintenance` via `CELERY_TASK_ROUTES`
**Notes:** `config/celery.py` already reserves the beat entry; today the task would silently land
on `default`. The decorator `name=` must match the reserved path exactly (6.2's recorded lesson).

### Throttling these public reads

| Option | Description | Selected |
|--------|-------------|----------|
| Add an anon `analytics_reads` throttle | Closes the cache-busting path on the app's costliest queries | ✓ |
| Follow the precedent — leave reads unthrottled | Consistent with community's read routes | |
| Rely on caching alone | No new throttle class | |

**User's choice:** Add an `analytics_reads` scope
**Notes:** Rationale given: cache keys multiply per filter combination, so an anonymous caller can
walk region × hiring_type × batch and force uncached computation every time. This deliberately
departs from community's unthrottled-reads precedent, where reads are paginated and
query-budgeted rather than aggregate scans. Exact rate left to Claude.

### Filter validation

| Option | Description | Selected |
|--------|-------------|----------|
| Whitelist-validate filters, 400 on unknown | Against model choices and `BATCH_YEARS`; bounded key space | ✓ |
| Ignore unknown filter values | Returns community-wide numbers for a typo | |
| Accept any filter string | Unbounded cache keys driven by anonymous input | |

**User's choice:** Whitelist-validate, 400 on unknown
**Notes:** Bounds the cache key space and turns a typo into a clear error instead of confidently
wrong data on a public stats page.

## ANAL-03's baseline

### Which interval the wait-time metric measures

| Option | Description | Selected |
|--------|-------------|----------|
| Make `READINESS_SURVEY` the primary baseline, offer as fallback | Requirement-literal and matches T7.7 | |
| Keep D1's offer-letter baseline and amend ANAL-03's text | One interval definition; rewrites the requirement to match the code | |
| Report both intervals as separate metrics | Spec's survey→JL and D1's offer→JL side by side, each with its own sample and floor | ✓ |

**User's choice:** Report both intervals as separate metrics
**Notes:** Context given: `READINESS_SURVEY` is both a `TimelineEvent` type and a
`CandidateProfile` status, the survey is later than the offer so the intervals differ materially,
and `12_SEED_DATA` gives only ≈20% of the seeded cohort a survey event — a survey-only metric
would frequently fall below the `<5` floor and suppress.

### Where the wait-time metric becomes visible

| Option | Description | Selected |
|--------|-------------|----------|
| Add it to the `/analytics/overview/` payload | No spec section defines a wait-time endpoint; the dashboard reads the cached payload | ✓ |
| Give it its own `/analytics/wait-times/` endpoint | Clean, filterable, but an invented API surface | |
| Leave it service-only in 7.2 | 7.1 already computes it; not exposed | |

**User's choice:** Expose through `/analytics/overview/`
**Notes:** 4.2's dashboard already serves threshold-suppressed community benchmarks, so it should
read from the same cached source rather than a second one.

### Counting deleted/anonymized accounts

| Option | Description | Selected |
|--------|-------------|----------|
| Exclude deleted/anonymized accounts from public analytics | Published numbers describe the present community | |
| Count them, as 7.1's aggregations do today | Counts stay stable and historical | ✓ |
| Exclude from cohorts, keep in wait-time samples | Split treatment | |

**User's choice:** Keep counting them, as today
**Notes:** Presented with 4.2's F1/F2 finding — account deletion anonymizes but retains the
profile row, so tombstones are counted in every cohort the public API will now serve. The
consequence is recorded in STATE.md as an accepted risk: every public number includes candidates
who have left, and the fix belongs with the retention model rather than an exposure phase.

### Disclosing a mixed baseline

| Option | Description | Selected |
|--------|-------------|----------|
| Disclose the baseline and per-baseline sample sizes | Each metric names its baseline and how many samples each source contributed | ✓ |
| Name the dominant baseline only | Cheapest honest signal | |
| Publish the aggregate only | A single average with a sample size | |

**User's choice:** Disclose baseline and per-source sample sizes
**Notes:** With two metrics published side by side this is what keeps them from being read as the
same number; within the offer→JL metric it also shows which of D1's four fallback steps resolved
each sample.

## Deferred Ideas

- **04 §52 `/analytics/timeline/`** — deferred to backlog; no requirement owns it, §108's required
  tests omit it, and it needs an event-level aggregation plus a per-day suppression rule.
- **OpenAPI/schema generation (04 §109)** — Phase 10.2 hardening; the project hand-writes its
  endpoint contracts and has no schema tooling.
- **Excluding deleted/anonymized accounts** — accepted, not deferred-as-forgotten (D-15); belongs
  with the retention model and recorded in STATE.md.
- **Per-chain-step suppression inside the wait-time sample** — a new rule if wanted, not part of
  the per-row floor.
- **A dedicated `analytics` queue and worker** — rejected in favour of `maintenance`.
- **Warming filtered combinations** — unfiltered defaults only; per-filter keys cache on first
  read.
