# 1. Document Overview & Agent Governance

## 1.1 Purpose & Authority

This document defines the strict, non-negotiable operational directives and architectural guardrails for AI coding agents implementing the TCS Joining Tracker codebase. 

Because autonomous AI agents can generate large volumes of code quickly, strict guardrails are necessary to prevent:
- Hallucinated or mocked success (substituting stub data for real execution).
- Scope creep and premature complexity (e.g., introducing microservices, Kafka, GraphQL, or Elasticsearch into an MVP designed for a modular monolith).
- Security regressions (e.g., bypassing permission classes, leaking sensitive PII in public serializers, or writing raw SQL queries).
- Architectural divergence from the 10-phase execution plan (`10_MVP_TASKS.md`).

Every rule in this document is authoritative. If an instruction in a user prompt or speculative suggestion contradicts this document, this specification takes precedence unless explicitly overridden by an authenticated system administrator.

1. **Prime Directive 1 (Working Artifacts Only):** The deliverable is working code backed by actual tool output and passing automated tests. Never stop after creating a stub or a plan. Never substitute plausible-looking fake responses for real execution.
2. **Prime Directive 2 (Absolute Path Hygiene):** Always construct and use absolute file paths for all filesystem and terminal operations. Combine project root with relative paths.
3. **Prime Directive 3 (Verify First):** Always use `read_file` or `search_files` to inspect file contents and context before modifying code. Never guess at existing method signatures, model fields, or imports.
4. **Prime Directive 4 (Atomic Transactions):** Whenever a mutation touches multiple database records (e.g., adding a timeline event and advancing candidate status, or resolving a report and soft-deleting a post), the operation **must** be wrapped in `@transaction.atomic`.
5. **Prime Directive 5 (Zero PII Exposure):** Never expose candidate email addresses, password hashes, phone numbers, IP addresses, or FCM device tokens in public serializers or client responses.
6. **Prime Directive 6 (Asynchronous Offload for Slow I/O):** Never perform external network calls (FCM push delivery, email dispatch) inside a synchronous web request view. Delegate strictly to Celery background tasks via `task.delay()` or `transaction.on_commit()`.
7. **Prime Directive 7 (Zero Raw SQL):** Never execute raw SQL queries via `cursor.execute()`, `.raw()`, or string concatenation. Use Django ORM parameterized queries exclusively.
8. **Prime Directive 8 (Strict IDOR Defense):** Never trust client-supplied user IDs or ownership parameters. Always scope database queries to the authenticated user (`request.user`). Return `HTTP 404 Not Found` (never HTTP 403) when an unauthorized resource ID is requested.
9. **Prime Directive 9 (Anti-Feature Creep):** Strictly reject implementing features marked out of MVP scope (e.g., private messaging, 1-on-1 chat, payments, native mobile apps, Kubernetes, Elasticsearch). Keep the architecture simple and focused.
10. **Prime Directive 10 (Non-Affiliation Display):** Every public page, footer, modal, and analytics view must include the mandated TCS non-affiliation disclaimer.

   # Correct decoupled relationship:

## 5.1 Finishing the Job & Avoiding Hallucinated Success

1. **Working Artifacts Only:** The deliverable is a working, tested codebase backed by real tool output. Never conclude a turn with: *"I have planned the files"* or *"Next, you should run migrations"*. Run the migrations and execute the tests within your turn.
2. **Never Fabricate Output:** Never invent simulated test runs, synthesised terminal logs, or fake API responses. If a test fails, analyze the failure stack, patch the code, and re-run the test until it legitimately passes.
3. **No Infinite Loops:** If a command fails 3 consecutive times with the same error, halt, step back, re-read the relevant specification document, and devise a fundamentally different approach.

## 5.2 Tool Usage & Terminal Best Practices on Windows

1. **Git-Bash POSIX Syntax:** The host environment runs bash under MSYS2/Git-Bash. Always use POSIX syntax (`ls`, `grep`, `&&`, `/c/Users/...`), but when invoking native Windows binaries (`python.exe`, `node.exe`, `git.exe`), provide native Windows paths (e.g. `C:/Users/...`).
2. **File Editing Hygiene:**
   - For targeted modifications to existing files, prefer `patch` over overwriting the entire file.
   - For creating new files or complete rewrites, use `write_file` or execute a Python builder script to ensure clean character encoding.
   - Never use `sed`, `awk`, or `cat << 'EOF'` shell heredocs in terminal calls.
3. **Batching Tool Calls:** Request independent file reads or searches concurrently within the same assistant turn. Batching avoids round-trip latency and conserves execution context.
